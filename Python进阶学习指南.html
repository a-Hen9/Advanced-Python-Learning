第 1 章 闭包与装饰器

本章目标：掌握 Python 的作用域规则；能解释闭包是什么、何时产生、有什么坑；能独立编写函数装饰器、带参装饰器、类装饰器，并理解 functools.wraps、@property 等内置装饰器的原理。

装饰器是 Python 生态的"通用语言"：pytest 的 fixture、Flask/FastAPI 的路由、@dataclass、@lru_cache 全部构建在这套机制上。这一章是后续所有章节的地基。

1.1 作用域：LEGB 规则

要理解闭包，先要理解"名字是如何被查找的"。Python 按 LEGB 顺序查找一个名字：

层级 全称 含义
L Local 函数内部（局部作用域）
E Enclosing 外层嵌套函数的作用域
G Global 模块（文件）级作用域
B Built-in 内置作用域（print、len 等） 
x = "global"                      # G

def outer():
    x = "enclosing"               # E
    def inner():
        x = "local"               # L
        print(x)                  # 按顺序找到了 L
    inner()

outer()                           # 输出: local

赋值语句决定作用域归属

关键规则：在函数内对某个名字赋值，这个名字就会被 Python 编译期判定为局部变量——即使外层存在同名变量。

count = 0

def broken():
    count = count + 1   # UnboundLocalError!
    # Python 认为 count 是局部变量（因为有赋值），
    # 但取值时它还没有被赋值

broken()

两种修复方式：

count = 0

def use_global():
    global count        # 声明：这里的 count 指全局变量
    count += 1

def nested():
    total = 0
    def add():
        nonlocal total  # 声明：这里的 total 指外层函数的变量
        total += 1      # nonlocal 不会一直往外找，只到最近的 enclosing 层
        return total
    add()
    add()
    return total        # 2

工程建议：global 尽量少用（可变的全局状态是 bug 温床）；nonlocal 是闭包读写外层变量的正规手段。

1.2 闭包（Closure）

1.2.1 定义：函数 + 捕获的环境

当内层函数引用了外层函数的变量，并且外层函数把内层函数作为返回值返回时，就形成了闭包——内层函数"记住"了定义它时所处的外层变量，即使外层函数已经执行完毕。

def make_multiplier(factor):
    """工厂函数：按需生成"乘以 factor"的函数"""
    def multiply(x):
        return x * factor      # factor 是自由变量，被 multiply 捕获
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)

print(double(10))    # 20
print(triple(10))    # 30

make_multiplier(2) 早已执行结束，但 double 依然记得 factor=2。这就是闭包。

1.2.2 直接观察闭包：__closure__

每个闭包函数都有一个 __closure__ 属性，存放它捕获的变量（以 cell 对象形式）：

print(double.__closure__)
# (<cell at 0x...: int object at 0x...>,)

print(double.__closure__[0].cell_contents)   # 2
  • 若函数没有捕获任何外层变量，__closure__ 为 None。
  • 这也是判断"我的 lambda/函数是不是闭包"的可靠方法。

1.2.3 用闭包实现有状态的对象

闭包可以替代简单的类，实现"携带内部状态"的功能：

def make_counter():
    count = 0
    def increment():
        nonlocal count        # 没有这行就只是"读"，无法自增
        count += 1
        return count
    return increment

counter_a = make_counter()
counter_b = make_counter()    # 每次调用工厂，得到互相独立的新环境

print(counter_a(), counter_a(), counter_a())   # 1 2 3
print(counter_b())                             # 1  ← 与 counter_a 互不影响

闭包 vs 类：状态少、逻辑简单时闭包更轻量；状态多、行为多时用类更清晰。工厂函数 + 闭包是很多库源码里的惯用手法。

1.3 闭包的经典陷阱：捕获的是变量，不是值

闭包捕获的是变量本身（绑定），而不是变量当时的值。

funcs = []
for i in range(3):
    funcs.append(lambda: i)

print([f() for f in funcs])    # [2, 2, 2]  ← 不是 [0, 1, 2]！

原因：三个 lambda 捕获的都是同一个变量 i（外层作用域里只有这一个 i），循环结束后 i 的最终值是 2，所有 lambda 读到的自然都是 2。

两种修复方式：

# 方式一：默认参数在"定义时"求值，相当于拍照存档
funcs = [lambda i=i: i for i in range(3)]
print([f() for f in funcs])    # [0, 1, 2]

# 方式二：再套一层工厂函数，每个 lambda 有自己的 enclosing 环境
def make(i):
    return lambda: i
funcs = [make(i) for i in range(3)]
print([f() for f in funcs])    # [0, 1, 2]

同类陷阱还会出现在延迟执行场景：回调注册、事件绑定、多线程传任务、pytest 中在循环里定义断言函数……只要"定义时"和"调用时"时间分离，就要警惕。

1.4 装饰器：闭包的杀手级应用

1.4.1 本质：装饰器只是一个"接收函数、返回函数"的函数

import functools
import time

def timer(func):
    """统计被装饰函数的执行耗时"""
    @functools.wraps(func)                 # 1.4.3 详解，先记住必须写
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)     # 调用原函数
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} 耗时 {elapsed:.4f}s")
        return result                      # 必须返回原函数的结果
    return wrapper

@timer                       # 语法糖
def work(n):
    return sum(range(n))

print(work(10_000_000))
# work 耗时 0.1873s
# 49999995000000

@timer 只是语法糖，完全等价于：

def work(n):
    return sum(range(n))
work = timer(work)     # 名字 work 现在指向 wrapper

理解了这行等价代码，装饰器就没有任何魔法可言。

1.4.2 带"装饰器参数"的装饰器：三层嵌套

如果希望装饰器本身可以配置（如 @retry(times=5)），需要再包一层：

import functools
import time
import random

def retry(times=3, delay=1.0, exceptions=(Exception,)):
    """失败自动重试：times 次，每次间隔 delay 秒"""
    def decorator(func):                      # 第一层：接收配置，返回真正的装饰器
        @functools.wraps(func)
        def wrapper(*args, **kwargs):         # 第二层：真正的装饰器
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions as e:
                    if attempt == times:
                        raise                 # 最后一次失败：如实抛出
                    print(f"第 {attempt} 次失败({e})，{delay}s 后重试")
                    time.sleep(delay)
        return wrapper
    return decorator

@retry(times=3, delay=0.5, exceptions=(ConnectionError,))
def unstable_call():
    """模拟不稳定的网络请求"""
    if random.random() < 0.7:
        raise ConnectionError("网络抖动")
    return "success"

print(unstable_call())

记忆要点：@retry(times=3) 会先执行 retry(times=3) 得到真正的装饰器，再装饰函数。所以带参装饰器 = "装饰器工厂"。

1.4.3 为什么必须 functools.wraps？

不写 @functools.wraps(func) 时，被装饰后的函数丢失了原函数的元信息：

def bad_timer(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@bad_timer
def greet(name):
    """向某人问好"""
    return f"hello {name}"

print(greet.__name__)       # wrapper    ← 名字丢了
print(greet.__doc__)        # None       ← 文档丢了
help(greet)                 # 帮助信息完全错误，调试和文档生成都会受影响

加上 @functools.wraps(func) 后，__name__、__doc__、__module__、__wrapped__（指向原函数）等元信息都会被复制到 wrapper 上。这是装饰器的标准动作，永远不要省略。

1.4.4 类装饰器：需要保存状态或可配置实例时

装饰器也可以是一个实现了 __call__ 的类，天然能携带可变状态：

import functools

class CountCalls:
    """统计函数被调用的次数"""
    def __init__(self, func):
        functools.update_wrapper(self, func)   # 类版 wrapter 写法
        self.func = func
        self.count = 0

    def __call__(self, *args, **kwargs):
        self.count += 1
        print(f"第 {self.count} 次调用 {self.func.__name__}")
        return self.func(*args, **kwargs)

@CountCalls
def say_hi():
    print("hi")

say_hi()     # 第 1 次调用 say_hi / hi
say_hi()     # 第 2 次调用 say_hi / hi
print(say_hi.count)   # 2  ← 状态可以直接访问

选择标准：无状态或少量闭包变量 → 函数装饰器；需要多个可配置项、暴露状态、或实现接口 → 类装饰器。

1.4.5 多个装饰器的执行顺序

def deco_a(func):
    print("装饰阶段：a 生效")
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("调用阶段：a 的前置逻辑")
        result = func(*args, **kwargs)
        print("调用阶段：a 的后置逻辑")
        return result
    return wrapper

def deco_b(func):
    print("装饰阶段：b 生效")
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        print("调用阶段：b 的前置逻辑")
        return func(*args, **kwargs)
    return wrapper

@deco_a
@deco_b
def hello():
    print("hello 原函数")

# 模块加载时输出：
#   装饰阶段：b 生效     （自下而上装饰）
#   装饰阶段：a 生效
hello()
#   调用阶段：a 的前置逻辑
#   调用阶段：b 的前置逻辑   （自上而下执行）
#   hello 原函数
#   调用阶段：a 的后置逻辑

规则一句话：装饰时自下而上（靠近函数的先包），调用时自上而下（最外层的前置逻辑先跑）。等价于 hello = deco_a(deco_b(hello))。

1.5.1 @property：把方法伪装成属性

class Temperature:
    def __init__(self, celsius=0.0):
        self.celsius = celsius          # 实际会走 setter

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("温度不能低于绝对零度")
        self._celsius = value

    @property
    def fahrenheit(self):               # 只读派生属性，不带 setter
        return self._celsius * 9 / 5 + 32

t = Temperature(25)
print(t.celsius, t.fahrenheit)   # 25 77.0
t.celsius = 100                  # 像赋值一样触发校验
print(t.fahrenheit)              # 212.0

价值：对外保持"属性访问"的简洁 API，内部随时可以插入校验、缓存、日志逻辑而不破坏调用方代码。相关工具还有 functools.cached_property（首次访问后缓存结果，适合开销大的派生值）。

1.5.2 @staticmethod 与 @classmethod

class Date:
    def __init__(self, year, month, day):
        self.year, self.month, self.day = year, month, day

    @classmethod
    def from_string(cls, s):            # cls 指向当前类，子类调用时自动跟随子类
        y, m, d = map(int, s.split("-"))
        return cls(y, m, d)             # 备选构造器（最常见的 classmethod 用途）

    @staticmethod
    def is_valid_date(s):               # 与类状态无关的工具函数，只是"住"在类里
        parts = s.split("-")
        return len(parts) == 3 and all(p.isdigit() for p in parts)

d = Date.from_string("2026-10-01")
print(Date.is_valid_date("2026-13-99"))    # True（这里只演示结构，不做真校验）

1.5.3 @functools.lru_cache / @functools.cache：函数级缓存

import functools

@functools.lru_cache(maxsize=128)     # 缓存最近 128 组参数的结果
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(200))     # 瞬间出结果；不加缓存则是天文数字级的递归耗时

@functools.cache     # Python 3.9+，等价于 lru_cache(maxsize=None)，适合"参数空间小"的纯函数
def load_config(path):
    print(f"真的读取了 {path}")      # 同参数第二次调用不会执行到这里
    return {"path": path}

load_config("app.ini")
load_config("app.ini")   # 命中缓存

注意事项：

  • 缓存把"每次调用结果"都存起来，参数和返回值都会被强引用，不能用于参数空间无界或返回大对象、以及依赖外部可变状态的函数（那会返回过期结果）。
  • 实例方法上直接用 @lru_cache 会把 self 当作缓存键的一部分，导致实例无法被回收——应加在"模块级函数"或 @staticmethod 上，或改用 functools.cached_property。

模式二：结果缓存 + 失效控制（装饰器版的记忆化）

import functools
import time

def timed_cache(seconds: float, maxsize: int = 128):
    """带过期时间的 lru_cache：适合缓存"会随时间变化"的数据，如接口响应"""
    def decorator(func):
        cache = functools.lru_cache(maxsize=maxsize)(func)
        timestamps: dict[tuple, float] = {}

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            key = (args, tuple(sorted(kwargs.items())))
            now = time.monotonic()
            ts = timestamps.get(key)
            if ts is not None and now - ts > seconds:
                cache.cache_clear()          # 简化处理：整体清空
                timestamps.clear()
            result = cache(*args, **kwargs)
            timestamps[key] = now
            return result
        wrapper.cache_clear = cache.cache_clear
        return wrapper
    return decorator

@timed_cache(seconds=5)
def get_rate(currency):
    print(f"({currency}: 真实请求)")
    return 7.2

print(get_rate("USD"))   # (USD: 真实请求) / 7.2
print(get_rate("USD"))   # 7.2（命中缓存）

模式四：鉴权 / 前置校验（Web 框架的核心套路）

import functools

class PermissionDenied(Exception): pass

_CURRENT_USER = {"name": "alice", "roles": {"admin"}}

def require_role(role: str):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(user, *args, **kwargs):
            if role not in user.get("roles", set()):
                raise PermissionDenied(f"需要 {role} 权限")
            return func(user, *args, **kwargs)
        return wrapper
    return decorator

@require_role("admin")

    print(f"{operator['name']} 删除了用户 {target_id}")

delete_user(_CURRENT_USER, 42)          # alice 删除了用户 42
guest = {"name": "bob", "roles": set()}
delete_user(guest, 42)                  # PermissionDenied: 需要 admin 权限

1.7 常见陷阱清单

  1. 忘记 functools.wraps → 调试信息、文档、序列化全部异常。
  2. 装饰器里忘了 return result → 原函数返回值悄悄变成 None，极难排查。
  3. 用可变对象做默认参数（def f(items=[])）——与闭包无关但同属"定义时求值"陷阱，默认值只在函数定义时创建一次。
  4. 装饰器有副作用且依赖导入顺序：装饰代码在模块导入时执行，别在里面做耗时/依赖环境的操作。
  5. 给类方法加 @lru_cache → 实例泄漏（见 1.5.3）。
  6. 装饰器返回了新函数却改了签名：wrapper 必须用 *args, **kwargs 透传，配合类型注解可让 mypy 帮你把关（见第 09 章）。

1.8 本章小结

  • 名字查找按 LEGB；函数内的赋值使名字成为局部变量，需要跨层读写时用 nonlocal/global。
  • 闭包 = 内层函数 + 捕获的外层变量，捕获的是变量绑定而非值快照；循环变量陷阱用 i=i 默认参数或工厂函数化解。
  • 装饰器是接收函数返回新函数的调用约定，@ 只是 f = deco(f) 的语法糖；带参装饰器多一层工厂。
  • 永远 @functools.wraps；需要状态用类装饰器；property/lru_cache/singledispatch/dataclass 是标准库给的高频轮子。

第 2 章 迭代器与生成器

本章目标：分清"可迭代对象"和"迭代器"，理解 for 循环的真实工作方式；掌握生成器函数与生成器表达式；会用 send/yield from；能用生成器构建惰性数据处理管道，从容处理内存装不下的大数据；熟练使用 itertools。

2.1 迭代协议：for 循环背后发生了什么

2.1.1 两个角色：可迭代对象 vs 迭代器

概念 定义 判断方法
可迭代对象 Iterable 实现了 __iter__，能"提供"一个迭代器 isinstance(x, collections.abc.Iterable)
迭代器 Iterator 实现了 __next__（和 __iter__），是"一次性游标" isinstance(x, collections.abc.Iterator)

for 循环的真实工作方式——它并不是"遍历容器"，而是：

# for x in obj: 的等价展开
_it = iter(obj)            # 1. 调用 obj.__iter__() 拿到迭代器
while True:
    try:
        x = next(_it)      # 2. 反复调用迭代器的 __next__()
    except StopIteration:  # 3. 抛出 StopIteration 就结束循环
        break
    ...                    # 循环体

nums = [1, 2, 3]
it = iter(nums)

print(next(it))    # 1
print(next(it))    # 2
print(next(it))    # 3
next(it)           # StopIteration

# 列表是可迭代对象，不是迭代器
from collections.abc import Iterable, Iterator
print(isinstance(nums, Iterable))   # True
print(isinstance(nums, Iterator))   # False
print(isinstance(iter(nums), Iterator))   # True

2.1.2 为什么要有两层协议？

因为迭代器是一次性的，可迭代对象可以反复迭代：

nums = [1, 2, 3]
for x in nums:
    print(x, end=" ")     # 1 2 3
for x in nums:            # 第二次遍历依然完整
    print(x, end=" ")     # 1 2 3

每次 for 都向列表要一个全新的迭代器（iter(nums) 每次返回独立游标）。而生成器本身就是迭代器，穷尽后不能重来：

gen = (x * 2 for x in [1, 2, 3])
print(list(gen))    # [2, 4, 6]
print(list(gen))    # []  ← 已耗尽，不会报错但为空

2.1.3 自己实现迭代器

class Fibonacci:
    """迭代器：生成前 stop 个斐波那契数"""
    def __init__(self, stop):
        self.stop = stop
        self.a, self.b = 0, 1
        self.i = 0

    def __iter__(self):          # 迭代器的 __iter__ 返回自身
        return self

    def __next__(self):
        if self.i >= self.stop:
            raise StopIteration
        value = self.a
        self.a, self.b = self.b, self.a + self.b
        self.i += 1
        return value

print(list(Fibonacci(8)))    # [0, 1, 1, 2, 3, 5, 8, 13]

更规范的设计是"容器类 + 独立迭代器类"分离，容器可重复迭代（每次 __iter__ 返回新迭代器）：

class Countdown:
    """可迭代对象：每次 for 都能从头倒数"""
    def __init__(self, n):
        self.n = n

    def __iter__(self):
        return CountdownIterator(self.n)

class CountdownIterator:
    def __init__(self, n):
        self.cur = n

    def __iter__(self):
        return self

    def __next__(self):
        if self.cur <= 0:
            raise StopIteration
        self.cur -= 1
        return self.cur + 1

print(list(Countdown(3)))   # [3, 2, 1]
print(list(Countdown(3)))   # [3, 2, 1]  ← 可重复

顺带一提：__getitem__ 也支持 for 循环（老式协议，从下标 0 开始递增直到 IndexError），但新代码请实现 __iter__。

2.2 生成器：最简洁的迭代器写法

2.2.1 生成器函数

函数体里只要出现 yield，它就不再是普通函数——调用它不执行函数体，而是返回一个生成器对象（生成器就是迭代器）：

def countdown(n):
    print("生成器被创建，但还没开始执行")
    while n > 0:
        yield n            # 暂停在这里，交出值
        n -= 1             # next() 时从这里恢复
    print("生成器结束")

gen = countdown(3)          # ← 什么都没打印！函数体尚未执行
print(next(gen))            # 生成器被创建... → 3
print(next(gen))            # 2
print(next(gen))            # 1
next(gen)                   # 生成器结束 → StopIteration

yield 相当于"带书签的 return"：交出值并冻结全部局部状态，下次 next() 从冻结点继续。前面第 1 章手写的斐波那契迭代器，用生成器 4 行搞定：

def fib(stop):
    a, b = 0, 1
    for _ in range(stop):
        yield a
        a, b = b, a + b

print(list(fib(8)))         # [0, 1, 1, 2, 3, 5, 8, 13]

2.2.2 生成器表达式

squares = (x * x for x in range(10))     # 圆括号 = 生成器表达式
total = sum(x * x for x in range(10))    # 作为唯一实参时可省一层括号

与列表推导式的关键区别——内存占用：

import sys

lst = [x * x for x in range(1_000_000)]
gen = (x * x for x in range(1_000_000))

print(sys.getsizeof(lst))    # ~4,000,056 字节（8MB 级，装下全部元素）
print(sys.getsizeof(gen))    # ~200 字节（只装"怎么算"，不装结果）

选择经验：需要反复访问、求长度、切片 → 列表；只遍历一次（尤其是链式处理或数据量大） → 生成器。

2.2.3 生成器是"惰性"的

值只有在被要的时候才算，且算完即弃：

def show_yield():
    print("第一个")
    yield 1
    print("第二个")
    yield 2

gen = show_yield()
first = next(gen)      # 打印"第一个"，得到 1
# 如果程序到这里终止，"第二个"永远不会执行——没消费就不计算

这让"无限序列"成为可能：

def naturals():
    n = 0
    while True:          # 无限循环，但没人要就不算下一个
        yield n
        n += 1

from itertools import islice
print(list(islice(naturals(), 5)))   # [0, 1, 2, 3, 4]（islice 只取前 5 个）

2.3 生成器进阶：send、throw、close、yield from

2.3.1 send：向生成器内部传值

yield 不只能"发"值，还能"收"值——这是协程思想的雏形：

def running_average():
    total, count = 0.0, 0
    average = None
    while True:
        value = yield average        # yield 的返回值 = send 进来的值
        total += value
        count += 1
        average = total / count

avg = running_average()
next(avg)                # 预激（prime）：推进到第一个 yield，才能开始 send
print(avg.send(10))      # 10.0
print(avg.send(20))      # 15.0
print(avg.send(30))      # 20.0

注意：必须先 next(gen)（或 gen.send(None)）预激，让代码走到第一个 yield，否则 send 会报 TypeError: can't send non-None value to a just-started generator。装饰器可封装预激动作：

import functools

def coroutine(func):
    @functools.wraps(func)
    def start(*args, **kwargs):
        g = func(*args, **kwargs)
        next(g)
        return g
    return start

2.3.2 close 与 GeneratorExit

gen.close() 会在生成器暂停点抛出 GeneratorExit，用于通知生成器"不会再有人取值了"，可在其中做清理：

def db_query():
    try:
        rows = ["r1", "r2"]
        yield from rows
    finally:
        print("连接已释放")     # 无论耗尽、close 还是 GC 都会执行

g = db_query()
print(next(g))       # r1
g.close()            # 连接已释放

finally 块同样适用于 for 循环中途 break/异常导致的生成器遗弃（GC 时机不定，重要的清理别依赖它，显式 close() 或用 with 管理）。

2.3.3 yield from：委托子生成器并接收返回值

def inner():
    yield 1
    yield 2
    return "inner 完成"          # 生成器可以有返回值，经 StopIteration.value 传出

def outer():
    result = yield from inner()  # 逐个透传 inner 的值，并把返回值接住
    print(f"inner 返回: {result}")
    yield 3

print(list(outer()))    # inner 返回: inner 完成 / [1, 2, 3]

yield from iterable 等价于"for 循环逐个 yield"，但它还能透传 send/throw 双向通信，这是它与普通 for-yield 的本质区别，也是 Python 3.5 之前实现协程的标准手段（如今被 async/await 取代，但在纯生成器代码中仍然好用）。

# 扁平化嵌套结构：yield from 的典型应用
def flatten(nested):
    for item in nested:
        if isinstance(item, list):
            yield from flatten(item)     # 递归委托
        else:
            yield item

print(list(flatten([1, [2, [3, 4], 5], 6])))   # [1, 2, 3, 4, 5, 6]

2.4 实战：用生成器搭建惰性数据处理管道

处理 10GB 日志时，"读→过滤→解析→聚合"若每步都生成中间列表，内存必炸。生成器管道让数据像流水线一样逐条流动，任意时刻内存中只有一条记录：

import re
from pathlib import Path

# 准备一个示例日志文件
LOG = Path("access.log")
LOG.write_text(
    "\n".join([
        "2026-10-01 10:00:01 GET /index.html 200 1024",
        "2026-10-01 10:00:03 POST /api/login 401 128",
        "# 这是一行注释",
        "2026-10-01 10:00:09 GET /api/items 200 4096",
        "坏数据行",
        "2026-10-01 10:01:22 GET /api/items 500 64",
    ]),
    encoding="utf-8",
)

def read_lines(path):
    """阶段1：逐行读取（不一次读入整个文件）"""
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")

def valid_lines(lines):
    """阶段2：过滤掉注释和空行"""
    pattern = re.compile(r"^\d{4}-")
    return (l for l in lines if pattern.match(l))

def parse_lines(lines):
    """阶段3：解析成结构化记录"""
    for line in lines:
        parts = line.split()
        yield {"date": parts[0], "time": parts[1], "method": parts[2],
               "path": parts[3], "status": int(parts[4]), "bytes": int(parts[5])}

def only_5xx(records):
    """阶段4：筛出服务端错误"""
    return (r for r in records if r["status"] >= 500)

# 组装管道：惰性串联，不产生任何中间列表
pipeline = only_5xx(parse_lines(valid_lines(read_lines(LOG))))
for record in pipeline:
    print(record["time"], record["path"], record["status"])
# 10:01:22 /api/items 500

LOG.unlink()   # 清理示例文件

要点：每个阶段都返回生成器，管道直到 for 消费时才真正开始流动。这种风格与 Unix 管道 grep | awk | sort 同构，是处理流式数据的通用范式。

groupby 最容易用错——它只对相邻的相同键分组，通常要先排序：

data = [
    ("水果", "苹果"), ("水果", "香蕉"),
    ("蔬菜", "土豆"), ("水果", "橘子"),   # 注意：水果再次出现
]

# 错误用法：水果被拆成两组（相邻性决定）
for key, group in groupby(data, key=lambda x: x[0]):
    print(key, [v for _, v in group])
# 水果 ['苹果', '香蕉']
# 蔬菜 ['土豆']
# 水果 ['橘子']

# 正确用法：先按 key 排序
for key, group in groupby(sorted(data, key=lambda x: x[0]), key=lambda x: x[0]):
    print(key, [v for _, v in group])
# 水果 ['苹果', '香蕉', '橘子']
# 蔬菜 ['土豆']

islice/takewhile 与无限生成器组合，是"从无限流中按需取数"的标准姿势（见 2.2.3）。

2.6 常见陷阱清单

  1. 迭代器只能消费一次：gen 耗尽后再 list(gen) 得空列表。需要多次消费就写生成器函数（每次调用得到新迭代器），或存成列表。
  2. 生成器里抛出的异常延迟出现：错误发生在 next()/消费时，而非定义时，堆栈定位要往上找。
  3. 在生成器中修改正在迭代的集合（for x in lst: lst.remove(x)）→ 跳元素；应遍历副本 for x in lst[:] 或用列表推导重建。
  4. groupby 不排序 → 分组结果碎片化（见 2.5）。
  5. 拿生成器当序列用：不支持索引、len()、切片——要么转列表，要么用 islice。
  6. 默认参数放生成器：def f(x=[]) 同样只在定义时创建一次。
  7. 无限生成器配合 sum()/max()/list()：会永远算不完，务必先 islice/takewhile 截断。

2.7 本章小结

  • for 循环 = iter() + 反复 next() 直到 StopIteration；可迭代对象提供迭代器，迭代器是一次性游标。
  • 生成器函数（含 yield）是最简洁的迭代器实现，天然惰性，适合无限序列与大数据流。
  • send 让生成器反向收值（协程雏形）；yield from 委托子生成器并透传双向通信；finally 处理清理。
  • 惰性管道是内存友好的数据处理范式：读→过滤→解析→聚合逐级串联，逐条流动。
  • itertools + 生成器组合，几乎可以替代大多数手写循环。

第 3 章 上下文管理器与内存管理

本章目标：理解 with 语句的协议本质，会用 __exit__ 做异常控制；熟练使用 contextlib 构造各类上下文管理器；掌握 CPython 的引用计数 + 分代垃圾回收模型，能识别循环引用和常见内存泄漏，会用 __slots__ 和 weakref 优化内存。

3.1 with 语句：确定性的资源管理

3.1.1 为什么需要 with

文件、锁、网络连接、临时目录……都有"用完必须释放"的需求。依赖 finally 手工释放容易遗漏：

# 不推荐：一旦中间抛异常，f.close() 就没机会执行
f = open("data.txt", encoding="utf-8")
data = process(f.read())
f.close()

with 语句把"进入时准备、退出时清理"固化成协议，无论是否发生异常，清理动作保证执行：

with open("data.txt", encoding="utf-8") as f:
    data = process(f.read())
# 离开 with 块（正常结束或异常）时 f.__exit__ 被调用，文件一定被关闭

3.1.2 协议本质：__enter__ 与 __exit__

with 语句的等价展开：

mgr = (EXPR)
value = mgr.__enter__()          # as 后面的变量接收 __enter__ 的返回值
try:
    BODY
except Exception as e:
    exit_ok = mgr.__exit__(type(e), e, e.__traceback__)   # 异常路径
    if not exit_ok:
        raise                    # __exit__ 返回 False/None → 异常继续传播
else:
    mgr.__exit__(None, None, None)                        # 正常路径

自己实现一个计时上下文管理器：

import time

class Timer:
    def __init__(self, label="代码块"):
        self.label = label

    def __enter__(self):
        self.start = time.perf_counter()
        return self                    # as 变量拿到的是 self

    def __exit__(self, exc_type, exc_val, exc_tb):
        elapsed = time.perf_counter() - self.start
        suffix = "（发生异常）" if exc_type else ""
        print(f"[{self.label}] 耗时 {elapsed:.4f}s{suffix}")
        return False                   # False = 不吞异常；True = 抑制异常

with Timer("求和"):
    total = sum(range(1_000_000))
# [求和] 耗时 0.0312s

with Timer("会抛异常的块"):
    1 / 0
# [会抛异常的块] 耗时 0.0000s（发生异常）
# ZeroDivisionError: division by zero        ← 异常没有被吞掉

__exit__ 的三个参数是异常三元组 (异常类, 异常实例, traceback)；无异常时均为 None。返回 True 表示"异常我处理了，别再传播"——这是极少数应该谨慎使用的"吞异常"开关（典型正当用途：contextlib.suppress 的内部实现）。

3.1.3 多个上下文与实用细节

# 同一 with 中管理多个资源（Python 3.1+），等价于嵌套 with
with open("src.txt", encoding="utf-8") as src, open("dst.txt", "w", encoding="utf-8") as dst:
    dst.write(src.read())

注意 open() 返回的文件对象是"上下文管理器"，但它不是线程安全的，也不要在多个线程里共享同一个文件句柄。

3.2 contextlib：标准库的上下文管理工具箱

3.2.1 @contextmanager：用生成器函数替代类

大多数场景下，类模板太重。@contextmanager 把"装饰器 + 生成器"变成一把瑞士军刀：

import time
from contextlib import contextmanager

@contextmanager
def timer(label="代码块"):
    start = time.perf_counter()          # __enter__ 部分
    try:
        yield label                      # yield 前后即 enter/exit；yield 值给 as
    finally:
        elapsed = time.perf_counter() - start
        print(f"[{label}] 耗时 {elapsed:.4f}s")   # __exit__ 部分（必须放 finally）

with timer("推送任务") as name:
    print(f"正在执行: {name}")

事务模板（成功提交、失败回滚）——工程中最经典的 @contextmanager 用法：

@contextmanager
def transaction(conn):
    try:
        yield conn
        conn.commit()                    # with 块正常结束 → 提交
        print("事务已提交")
    except Exception:
        conn.rollback()                  # 块内任何异常 → 回滚
        print("事务已回滚")
        raise                            # 关键：回滚后继续抛出，不能吞

记忆口诀：yield 之前是 enter，finally 里是 exit；"带异常参数的 yield"（yield 出现在 except 子句里）可以拿到异常做定向处理，但 90% 的场景 try/finally 足够。

3.3 CPython 内存管理模型

3.3.1 一切皆引用：变量是"名字贴纸"

Python 中变量不存值，只是绑定到对象的引用（名字贴纸）。理解对象生命周期从引用计数开始：

import sys

a = [1, 2, 3]
print(sys.getrefcount(a))    # 2 —— a 本身 + getrefcount 的临时参数引用（天然 +1）

b = a                        # 第二张贴纸指向同一对象，不复制数据
b.append(4)
print(a)                     # [1, 2, 3, 4] —— a 和 b 是同一个对象

print(a is b)                # True：同一对象；== 比较值，is 比较"是不是同一个"

小整数（-5~256）和短字符串会被解释器驻留（interning）复用，这是性能优化，不要依赖它做逻辑判断。判断相等永远用 ==，只有判断"是否同一个对象/是否为 None"才用 is。

3.3.2 主体：引用计数（立即回收）

每个对象记录"有多少引用指向我"。计数归零的瞬间，对象立即销毁、内存立即归还——这就是 CPython 的主回收机制，也是 CPython 没有"析构时机不确定"问题的原因：

import sys

def make_big():
    return bytearray(10_000_000)     # 10MB

x = make_big()
print(sys.getsizeof(x))       # 10000048
x = None                      # 引用归零，10MB 立即释放（无需等 GC）

引用计数的致命弱点：循环引用（A 引用 B、B 引用 A，或对象引用自身），计数永远无法归零。

class Node:
    def __init__(self, name):
        self.name = name
        self.partner = None
    def __repr__(self):
        return f"Node({self.name})"

a = Node("a")
a.partner = a                 # 自引用
a_ref = a                     # 局部变量里还留着一份引用（此时在脚本顶层，等效全局）
del a                        # 还剩 a_ref 一份，不回收 —— 正常

3.3.3 补充：分代垃圾回收（专治循环引用）

CPython 用分代 GC 兜底处理循环垃圾：对象按存活时间分 0/1/2 三代（新对象在 0 代），GC 频率 0 代 > 1 代 > 2 代。默认阈值可用 gc.get_threshold() 查看，通常是 (700, 10, 10)：0 代分配计数超 700 触发一次 0 代回收，其中存活对象晋升 1 代……

import gc

class Node:
    def __init__(self):
        self.partner = None

a, b = Node(), Node()
a.partner = b
b.partner = a                  # 循环引用
a_self = b_self = None

del a, b                       # 两个 Node 的计数都不为 0（互相引用），引用计数无能为力

print(gc.collect())            # 手动触发全代回收，返回清理的"不可达对象"数（≥2）
                               # 即使不手动调用，分配压力也会自动触发分代回收
print(gc.get_threshold())      # (700, 10, 10) —— 可用 gc.set_threshold() 调优

工程上的实用结论：

  1. 95% 的场景不需要管 GC——引用计数已经即时处理了绝大多数对象。
  2. 需要留意的场景：批量处理海量对象后（如爬虫百万页面），可手动 gc.collect() 归还内存；GC 暂停影响延迟的实时服务，可 gc.freeze()/调阈值（高级话题，先知道有这回事）。
  3. __del__（终结器）不保证执行时机，且历史上有循环引用 + __del__ 的回收难题（PEP 442 后已基本解决）。清理资源请用 with / try-finally，不要依赖 __del__。

3.3.4 弱引用：不阻止回收的引用

缓存、注册表、观察者等场景中，我们想"在对象还活着时引用它，但绝不让它因此活下来"——用 weakref：

import weakref

class ExpensiveModel:
    pass

cache = weakref.WeakValueDictionary()    # 值是弱引用的字典

model = ExpensiveModel()
cache["m1"] = model

print(cache["m1"] is model)   # True —— 对象还活着，能取到
del model                     # 删除最后一个强引用 → 对象销毁，缓存自动"蒸发"
print(cache.get("m1"))        # None

这是"对象缓存不阻碍内存回收"的标准方案。weakref.ref、WeakKeyDictionary、WeakSet 同理。注意：int/str/tuple/list/dict 等内置类型不支持弱引用，自定义类的实例可以。

3.3.5 __slots__：给对象瘦身

默认情况下，每个实例都有一个 __dict__ 存属性，灵活但费内存。声明 __slots__ 后，实例不再有 __dict__，属性以固定槽位存放——百万级小对象的内存可省 40%~60%，还能防止拼写错误的属性被静默创建：

class PointDict:
    def __init__(self, x, y):
        self.x, self.y = x, y

class PointSlots:
    __slots__ = ("x", "y")           # 只允许这两个属性
    def __init__(self, x, y):
        self.x, self.y = x, y

p = PointSlots(1, 2)
print(hasattr(p, "__dict__"))    # False
p.z = 3                          # AttributeError —— 拼写错误立即暴露

# dataclass 一行开关同样效果（Python 3.10+）：
# @dataclass(slots=True)

代价与陷阱：

  • 不能动态添加 slots 之外的属性（这往往正是收益所在）。
  • 继承时要小心：子类若不声明 __slots__ = ()，会悄悄带回 __dict__，优化失效。
  • 与某些依赖 __dict__ 的机制（如某些序列化框架）不兼容，用前评估。

3.3.6 定位内存问题：tracemalloc 与泄漏高发区

tracemalloc.start()
data = [bytearray(1024) for _ in range(10_000)]     # 制造 10MB 占用
snapshot = tracemalloc.take_snapshot()

for stat in top:
    print(stat)       # 指出是哪一行分配了最多内存

常见内存泄漏来源自查清单：

来源 典型形态 对策

3.4 实战：可重入的数据库连接池上下文

把本章知识串起来：上下文管理器 + 计数 + 弱引用思想。

import queue
from contextlib import contextmanager

class ConnectionPool:
    """极简连接池：演示 with 管理借用/归还的确定性"""
    def __init__(self, size=2):
        self._pool = queue.Queue(maxsize=size)
        for i in range(size):
            self._pool.put(f"conn-{i}")     # 用字符串模拟连接对象

    @contextmanager
    def borrow(self):
        conn = self._pool.get(timeout=5)    # 拿不到会等待（生产者消费者雏形）
        try:
            yield conn
        finally:
            self._pool.put(conn)            # 无论成功失败，连接一定归还

pool = ConnectionPool()

with pool.borrow() as c1:
    print("使用", c1)
    with pool.borrow() as c2:
        print("同时使用", c1, c2)
        try:
            with pool.borrow() as c3:       # 池已空：最多等 5 秒
                pass
        except queue.Empty:
            print("池耗尽，等待超时 —— 泄漏的连接会在这里现形")
# 使用 conn-0 / 同时使用 conn-0 conn-1 / 池耗尽...

核心思想：把"获取资源 → try: 使用 → finally: 归还"的模式封装成上下文管理器后，调用方再也不可能忘记归还——这是上下文管理器最大的工程价值。

3.5 常见陷阱清单

  1. 在 @contextmanager 里漏掉 try/finally：块内一抛异常，yield 之后的清理代码就不执行了。
  2. __exit__ 误返回 True 吞掉所有异常：除非刻意写 suppress 类工具，否则返回 False/None。
  3. 依赖 __del__ 释放关键资源：时机不保证；一律用 with 或 try/finally。
  4. 以为 is 能比较值：小整数/短字符串驻留让 a is b "碰巧"成立，换到其他值就翻车；等值判断只用 ==。
  5. 循环引用携带大对象：引用计数回收不了，靠分代 GC 兜底；长驻服务注意显式断环。
  6. __slots__ 继承陷阱：子类忘写 __slots__ = () 优化失效。
  7. gc.disable() 当性能优化无脑用：循环垃圾会无限堆积；只在确认"分配模式安全"的极特殊场景使用。

3.6 本章小结

  • with = __enter__/__exit__ 协议，清理确定性执行；__exit__ 返回 True 才吞异常。
  • @contextmanager 用生成器写上下文（yield 前后即 enter/exit，finally 兜底）；suppress/closing/ExitStack 覆盖大多数工具场景。
  • CPython 回收 = 引用计数（即时、主体）+ 分代 GC（兜底循环引用）；资源清理靠协议不靠析构函数。
  • __slots__ 省内存、防误加属性；weakref 让缓存不延长对象寿命；无界缓存是内存泄漏头号来源。

4.1 文件读写的正确姿势

4.1.1 模式与参数：把 open 用明白

open(file, mode="r", buffering=-1, encoding=None, errors=None, newline=None)
mode 含义 说明
r 只读（默认） 文件不存在抛 FileNotFoundError

  1. 读文本必配 with（原因见第 3 章）。
  2. 二进制模式没有 encoding——给它传 encoding 会直接报错，这是初学者高频错误。

4.1.2 读的四种方式与内存行为

with open("sample.txt", encoding="utf-8") as f:
    text = f.read()          # ① 一次性读入全部 → 小文件 OK，大文件爆内存

    chunk = f.read(4096)     # ② 指定字节数分块读（需 f.seek(0) 回到开头）

    lines = f.readlines()    # ③ 全部行装进列表 → 本质还是全量读

# ④ 推荐：文件对象本身是迭代器（第 2 章），逐行惰性读取，内存恒定
with open("big.log", encoding="utf-8") as f:
    for line in f:                    # 逐行流式处理
        if "ERROR" in line:
            print(line, end="")

写入的对应写法：

4.1.3 缓冲与三种 IO 流

Python 的 IO 分三层（io 模块）：

  • RawIOBase：原始系统调用层（open(..., buffering=0)）；
  • BufferedIOBase：带缓冲层（默认，减少系统调用次数）；
  • TextIOBase：文本层，负责编码解码与换行转换（open 默认返回 TextIOWrapper）。

newline 参数值得专门认识：文本模式默认开启通用换行（\r\n/\r/\n 都识别为 \n，写入时 \n 转成系统默认）。写 CSV 时必须 newline="" 让 csv 模块自己控制换行（4.5.2）。

内存文件——不需要真实磁盘时用 StringIO/BytesIO，单测里构造"伪文件"尤其方便：

sio.write("hello\nworld")
print(sio.getvalue())          # hello\nworld（无需真正落盘）

bio = BytesIO()
bio.write(b"\x89PNG\r\n")      # 二进制内存文件，常用于拼装图片/压缩包
print(bio.tell())              # 6 —— 二进制模式按字节定位

4.4.1 大文件三原则

  1. 逐行/逐块，绝不全量 read()（4.1.2 的方式④/②）。

4.4.2 struct：在字节流与 Python 值之间转换

解析二进制协议/文件头（如 PNG、网络包）时，struct 按格式字符串打包/解包：

import struct

# 格式 "<I4sf"：小端 + 4字节无符号整数 + 4字节字符串 + 4字节浮点
packed = struct.pack("<I4sf", 7, b"HEAD", 3.14)
print(packed)                    # b'\x07\x00\x00\x00HEAD\xdb\x0fI@'（12 字节）
print(len(packed))

magic, tag, value = struct.unpack("<I4sf", packed)
print(magic, tag, value)         # 7 b'HEAD' 3.140000104904175

print(struct.calcsize("<I4sf"))  # 12 —— 预先计算结构大小

常用格式符：B=uint8、H=uint16、I=uint32、Q=uint64、f=float32、d=float64、Ns=N 字节字符串；< 小端、> 大端。网络协议通常大端（>），文件格式看规范。

4.5.1 JSON：跨语言数据交换的标准

import json
from datetime import datetime

data = {
    "name": "张三",
    "scores": [90, 85],
    "created_at": datetime.now(),
}

def json_default(o):
    """处理 json 不认识的类型"""
    if isinstance(o, datetime):
        return o.isoformat()
    raise TypeError(f"无法序列化 {type(o).__name__}")

text = json.dumps(data, ensure_ascii=False, indent=2, default=json_default)
print(text)          # {"name": "张三", ..., "created_at": "2026-10-03T..."}

parsed = json.loads(text)
print(parsed["created_at"])       # 字符串 —— JSON 没有日期类型，读回来要自己转

# 文件版
with open("data.json", "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False, indent=2)
with open("data.json", encoding="utf-8") as f:
    data2 = json.load(f)

4.6 实战：一个健壮的"配置 + 缓存"文件模块

综合运用：pathlib、JSON、原子写入、异常处理。

import json
import os
from pathlib import Path

class ConfigStore:
    """基于 JSON 文件的配置存取：带原子写入，避免写一半崩溃产生损坏文件"""
    def __init__(self, path: str | Path):
        self._path = Path(path)
        self._path.parent.mkdir(parents=True, exist_ok=True)

    def load(self) -> dict:
        try:
            return json.loads(self._path.read_text(encoding="utf-8"))
        except FileNotFoundError:
            return {}                          # 首次使用
        except json.JSONDecodeError as e:
            raise ValueError(f"配置文件损坏: {self._path}") from e

    def save(self, data: dict) -> None:
        tmp = self._path.with_suffix(self._path.suffix + ".tmp")
        tmp.write_text(
            json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8"
        )
        os.replace(tmp, self._path)            # 原子替换（同盘 rename 是原子的）

store = ConfigStore("settings/app.json")
cfg = store.load()
cfg.setdefault("theme", "dark")
store.save(cfg)
print(store.load())        # {'theme': 'dark'}

"先写临时文件再 os.replace"是落盘的原子写惯用法——任何配置、状态文件都值得这样做。

4.7 常见陷阱清单

  1. 不传 encoding：跨机器 UnicodeDecodeError（GBK vs UTF-8）；一律显式指定。
  2. w 模式当"更新"用：open(path, "w") 一瞬间就清空了整个文件——只想更新请读入后用 r+/回写，或读出来改完走原子写。
  3. f.read() 处理大文件：内存爆炸；逐行迭代或分块读。
  4. CSV 忘记 newline=""：Windows 下每个记录后多一个空行。
  5. json.load 后把字符串日期当日期用：JSON 无日期类型，读回全是字符串，需要 datetime.fromisoformat 转换。
  6. 用 pickle 传递不受信数据：任意代码执行风险（4.5.3 红线）。
  7. 路径硬编码 / 或 \\、手工拼字符串：一律 pathlib.Path 的 / 运算符。
  8. 写文件后立即被其他程序读取失败：忘了 with 退出时才 flush；跨进程共享时用原子写（4.6）。

本章目标：深入理解 GIL 并能说清"多线程到底什么时候有用"；掌握 threading 的锁与同步原语；能诊断并避免竞态条件与死锁；熟练使用 queue.Queue 与 ThreadPoolExecutor 构建并发 IO 程序。

5.1 先搞懂 GIL：多线程的"枷锁"与"真相"

5.1.1 GIL 是什么

GIL（Global Interpreter Lock，全局解释器锁）是 CPython 解释器中的一把全局互斥锁：同一时刻，只允许一个线程执行 Python 字节码。

它存在的原因：CPython 的内存管理（引用计数）不是线程安全的。obj.refcount += 1 这类操作若无全局锁保护，多线程下计数会错乱，导致内存泄漏或提前释放。GIL 用"一把大锁"换来了实现简单与单线程性能。

关键事实：

  • GIL 锁的是字节码执行，不是整个 Python 进程的"所有事情"。
  • 线程在执行 IO 操作（网络、磁盘）、time.sleep()、以及许多 C 扩展的计算（如 hashlib、numpy 大块运算）时会主动释放 GIL，让其他线程运行。
  • 解释器每隔一段时间（默认 5ms，sys.getswitchinterval()）强制当前线程让出 GIL，保证"有机会公平轮转"。

5.1.2 用实验验证 GIL 的边界

实验一：CPU 密集任务——多线程不加速，甚至更慢

import threading
import time

def cpu_task():
    count = 0
    for i in range(10_000_000):
        count += i * i

def bench(label, runner):
    start = time.perf_counter()
    runner()
    print(f"{label}: {time.perf_counter() - start:.2f}s")

bench("串行 4 次", lambda: [cpu_task() for _ in range(4)])

threads = [threading.Thread(target=cpu_task) for _ in range(4)]
bench("4 线程", lambda: ([t.start() for t in threads], [t.join() for t in threads]))
# 典型输出（8 核机器）：
# 串行 4 次: 1.8s
# 4 线程:   1.9s   ← 完全没有加速！GIL 让字节码执行串行化了，还多了切换开销

实验二：IO 密集任务——多线程加速明显

def io_task():
    time.sleep(1)          # sleep 会释放 GIL，模拟网络/磁盘等待

bench("串行 4 次", lambda: [io_task() for _ in range(4)])

threads = [threading.Thread(target=io_task) for _ in range(4)]
bench("4 线程", lambda: ([t.start() for t in threads], [t.join() for t in threads]))
# 串行 4 次: 4.0s
# 4 线程:   1.0s   ← 等待期间 GIL 已释放，4 个"等待"并行进行

结论（必背）：

  • CPU 密集（数值计算、图像处理、编解码）→ 多线程无效 → 用多进程（第 6 章）。
  • IO 密集（网络请求、文件读写、数据库查询）→ 多线程有效且实现简单。
  • C 扩展是否释放 GIL 决定了 numpy/pandas 这类库的行为：numpy 大数组运算底层是 C 并释放 GIL，因此"用 numpy 的代码"多线程也可能加速。

前瞻：Python 3.13 提供了实验性的 free-threaded 构建（PEP 703，移除 GIL），3.14 起该构建转为受官方支持的选项（默认构建仍带 GIL）。未来 CPU 密集多线程会逐渐可用，但当前生态与默认发行版仍以本章模型为准。

5.2 threading 基础

5.2.1 创建与管理线程

import threading
import time

def worker(task_id, duration):
    print(f"线程-{task_id} 开始（当前线程: {threading.current_thread().name}）")
    time.sleep(duration)
    print(f"线程-{task_id} 结束")

t1 = threading.Thread(target=worker, args=(1, 1.5), name="下载线程")
t2 = threading.Thread(target=worker, args=(2, 0.5), name="解析线程")

t1.start()                     # start() 才启动新线程；直接调用 worker() 只是普通函数调用
t2.start()
t1.join()                      # join：等待该线程结束（主线程阻塞在此）
t2.join()
print("全部完成")

print(threading.active_count())   # 存活线程数

daemon=True（守护线程）：主线程退出时守护线程被直接杀死（没有清理机会）。适合心跳、监控类"陪跑"任务；不要让守护线程写文件/发请求——可能写到一半被杀：

monitor = threading.Thread(target=heartbeat, daemon=True)
monitor.start()

5.2.2 传递结果与异常

线程函数的返回值会被丢弃，异常也只打印堆栈不向上传播。获取结果的正确方式是"共享容器或队列"：

results = {}
def fetch(key, results):
    results[key] = f"{key} 的数据"

threads = [threading.Thread(target=fetch, args=(k, results)) for k in ("a", "b")]
for t in threads: t.start()
for t in threads: t.join()
print(results)     # {'a': 'a 的数据', 'b': 'b 的数据'}

# 传递"可调用对象"的自定义线程类（面向对象风格）
class MyTask(threading.Thread):
    def __init__(self, url):
        super().__init__()
        self.url = url
        self.result = None
    def run(self):                    # 覆写 run，start() 会自动调用它
        self.result = f"GET {self.url}"

5.4 的 ThreadPoolExecutor 用 Future 对象优雅地解决了"拿结果、传异常"问题，生产代码优先用它。

5.3 线程安全：竞态条件与锁

5.3.1 竞态条件：看得见的 bug

import threading

counter = 0

def increment(n=100_000):
    global counter
    for _ in range(n):
        counter += 1        # 看似一行，实为三步：读 → 加一 → 写回

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()

print(f"最终计数: {counter}（期望 {200_000}）")
# 典型输出: 最终计数: 112347（期望 200000）  ← 每次运行都不同！

counter += 1 是三条字节码：LOAD、ADD、STORE。两个线程可能同时读到旧值、各自加一、再写回——一次自增凭空丢失。GIL 并不能防止这种逻辑上的竞态（GIL 只保证字节码不交错，不保证"多字节码操作"的原子性）。

修复：加锁

import threading

counter = 0
lock = threading.Lock()          # 锁本身是线程安全的

def increment(n=100_000):
    global counter
    for _ in range(n):
        with lock:               # with 自动释放锁（第 3 章！异常也安全）
            counter += 1
# 修复后输出恒为 200000

粒度原则：锁只包住"读改写共享数据"的最小代码段。整个循环都锁住虽然结果对，但并发度归零。

5.3.2 锁的家族

原语 特点 典型场景
Lock 互斥锁，不可重入 保护临界区（首选）
RLock 可重入锁：同一线程可多次获取 同类方法互相调用都需持锁
Semaphore(n) 计数信号量，允许 n 个线程同时进入 限流：数据库连接池、并发上限
Event 一站式广播旗标 "准备就绪了，大家可以开始"
Condition 复杂条件等待/通知 缓冲区不满不生产、不空不消费
Barrier(n) n 个线程互相等齐再一起跑 多线程分阶段同步 
# RLock：可重入，避免"自己锁死自己"
class Bank:
    def __init__(self):
        self.balance = 1000
        self.lock = threading.RLock()     # 若用 Lock，transfer 会死锁

    def withdraw(self, amount):
        with self.lock:
            self.balance -= amount

    def transfer(self, other, amount):
        with self.lock:                   # 已持有 → RLock 允许再次进入
            self.withdraw(amount)
            other.balance += amount

# Semaphore：最多同时 3 个线程访问"数据库"
db_slots = threading.Semaphore(3)

def query(sql):
    with db_slots:
        ...  # 第 4 个线程会在这里等待前面的释放

# Event：等待初始化完成
ready = threading.Event()

def consumer():
    ready.wait(timeout=10)          # 阻塞直到 set()，可设超时
    print("收到就绪信号，开始消费")

def producer():
    ...
    ready.set()

# Barrier：赛跑发令枪
gate = threading.Barrier(3)         # 3 个线程都到齐后一起放行
# 每个 worker: gate.wait() → 同步点

5.3.3 死锁：两个锁、交叉等待

import threading
import time

lock_a = threading.Lock()
lock_b = threading.Lock()

def worker_1():
    with lock_a:
        time.sleep(0.1)          # 制造交叉窗口
        with lock_b:             # 等 lock_b（被 worker_2 持有）
            print("worker_1 完成")

def worker_2():
    with lock_b:
        time.sleep(0.1)
        with lock_a:             # 等 lock_a（被 worker_1 持有）→ 死锁！
            print("worker_2 完成")

# t1 = threading.Thread(target=worker_1); t2 = threading.Thread(target=worker_2)
# t1.start(); t2.start()   ← 演示用，真实运行会永久卡死

避免死锁的实践：

  1. 全局统一加锁顺序（如始终先 a 后 b）——最有效的方法；
  2. 一次持有多把锁时，用 lock.acquire(timeout=...) 超时放弃并重试；
  3. 缩小锁粒度、缩短持锁时间，能一把锁就别用两把；
  4. 用队列把"共享 + 加锁"整体消灭（见 5.5，最推荐）。

5.3.4 哪些操作是线程安全的？

  • 单条字节码级别的读/写（如 lst.append(x)、dict[key] = v）由解释器保证原子性；
  • "检查再行动"（check-then-act）永远不安全：if key not in d: d[key] = v 两步之间可被插入；
  • 复合操作不安全：counter += 1、d[k] = d.get(k, 0) + 1 都要加锁；
  • 更新原则：能换数据结构的就换——queue.Queue 天生线程安全（内部用锁 + Condition 封装好了），多数业务用它就不必手工加锁。

5.4 ThreadPoolExecutor：生产代码的首选

concurrent.futures 用 Future（未来结果）对象封装了线程管理，代码量减半且能拿返回值、收异常：

import time
from concurrent.futures import ThreadPoolExecutor, as_completed

def fetch(url: str) -> str:
    time.sleep(1)                    # 模拟网络请求（会释放 GIL）
    return f"{url} 的响应"

urls = [f"https://example.com/page/{i}" for i in range(1, 9)]

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:      # 离开 with 自动等待所有任务
    # 方式一：submit + as_completed —— 谁先完成先处理谁
    futures = {pool.submit(fetch, url): url for url in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            print(fut.result(timeout=None))          # 取结果；任务抛的异常在这里重新抛出
        except Exception as e:
            print(f"{url} 失败: {e}")

    # 方式二：map —— 结果按提交顺序返回，代码最短
    # for result in pool.map(fetch, urls): ...
    #   注意 map 的异常在迭代到对应元素时抛出

print(f"总耗时 {time.perf_counter() - start:.1f}s")
# 8 个任务 × 1s，4 并发 → 约 2s（串行需要 8s）

要点：

  • max_workers 不是越大越好：线程切换与 GIL 争用有成本，IO 密集一般 32~100 足够（默认值会按 CPU 数与 Python 版本智能取）。
  • Future 的 .result() 会重新抛出任务中的异常——这是相对裸 Thread 的巨大优势。
  • Python 3.9+ 可 fut.cancel() 取消还没开始的任务；pool.shutdown(wait=False, cancel_futures=True)（3.9+）快速丢弃未执行任务。

5.5 queue.Queue：用"消息传递"取代"共享内存"

并发编程的金科玉律（Go 语言的格言，同样适用于 Python）：

不要通过共享内存来通信，而要通过通信来共享内存。

多个线程不再直接读写同一份可变数据，而是把数据作为不可变消息放进线程安全队列：

import queue
import threading
import time

def producer(q: queue.Queue, n_items: int):
    for i in range(n_items):
        time.sleep(0.1)                  # 生产耗时
        q.put(f"任务-{i}")               # 队列满时阻塞（背压）
    for _ in range(N_CONSUMERS):
        q.put(None)                      # 毒丸（sentinel）：通知消费者收工

def consumer(q: queue.Queue, worker_id: int):
    while True:
        item = q.get()
        if item is None:
            break                        # 收到毒丸，退出
        time.sleep(0.3)                  # 消费耗时
        print(f"消费者-{worker_id} 处理完 {item}")
        q.task_done()

N_CONSUMERS = 3
q = queue.Queue(maxsize=10)              # 有限容量：生产过快时自动"背压"

threads = [threading.Thread(target=producer, args=(q, 5), daemon=True)]
threads += [threading.Thread(target=consumer, args=(q, i)) for i in range(N_CONSUMERS)]
for t in threads: t.start()
for t in threads[1:]: t.join()           # 等消费者结束
print("全部任务处理完毕")

Queue 三兄弟：Queue（FIFO）、LifoQueue（栈）、PriorityQueue（元组 (优先级, 序号, 数据) 按优先级出队）。q.join() + task_done() 是"毒丸"之外的另一种优雅收工方式：生产者完成后 q.join() 阻塞到所有条目被处理完。

5.6 实战：并发批量下载器（线程池版）

import time
from concurrent.futures import ThreadPoolExecutor, as_completed
from pathlib import Path
from urllib.request import urlopen

def download(url: str, dest_dir: Path) -> Path:
    dest = dest_dir / (url.rstrip("/").split("/")[-1] + ".html")
    with urlopen(url, timeout=10) as resp:       # 阻塞式 IO，多线程在此并行
        dest.write_bytes(resp.read())
    return dest                                  # 返回 Future 的 result

def download_all(urls: list[str], dest_dir: Path, workers: int = 8):
    dest_dir.mkdir(parents=True, exist_ok=True)
    ok, failed = [], []
    with ThreadPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(download, u, dest_dir): u for u in urls}
        for fut in as_completed(futures):
            url = futures[fut]
            try:
                ok.append(fut.result())
            except Exception as e:
                failed.append((url, repr(e)))    # 单个失败不影响整体
    return ok, failed

# ok, failed = download_all(["https://example.com/", "https://www.python.org/"], Path("downloads"))
# print(f"成功 {len(ok)} 个，失败 {len(failed)} 个")

这个骨架（submit + as_completed + 异常收集）就是绝大多数并发 IO 任务的通用模板，替换 download 函数即可复用。

5.7 常见陷阱清单

  1. 以为 GIL 能保证线程安全：counter += 1、check-then-act 照样竞态；共享可变状态必须加锁或走队列。
  2. 在守护线程里写文件/发请求：主线程退出即被杀，数据可能截断。
  3. 锁忘了 with 或 finally 释放：临界区内抛异常 → 锁永远不释放 → 整个程序挂死。永远 with lock:。
  4. 嵌套多锁无序：死锁（5.3.3），统一加锁顺序。
  5. 线程数开太大：切换开销 + GIL 争用反而更慢；IO 密集几十个足够。
  6. run() 与 start() 混淆：t.run() 是当前线程里普通调用，没有并发。
  7. 共享数据用"可变默认参数"或模块级全局：同样制造隐藏的共享状态。
  8. 用 time.sleep 当同步手段：竞态条件的时间赌局，用 Event/Condition/Queue。

5.8 本章小结

  • GIL 使同一时刻只有一个线程执行字节码；IO 等待与多数 C 扩展会释放 GIL，因此多线程适合 IO 密集、不适合 CPU 密集。
  • 线程安全的核心：保护"读改写"与"检查再行动"，with lock: 包最小临界区；能不用共享就不用——queue.Queue 消息传递是首选架构。
  • 同步原语按需选用：Lock/RLock/Semaphore/Event/Condition/Barrier。
  • 生产代码用 ThreadPoolExecutor：submit + as_completed 模板，Future 自动传递结果与异常。

第 6 章 多进程编程

本章目标：掌握 multiprocessing 与 ProcessPoolExecutor 的用法；理解 fork/spawn 启动方式差异与 if __name__ == "__main__" 的必要性；会用 Queue/Pipe/共享内存/Manager 做进程间通信；建立"线程 vs 进程 vs 协程"的选型能力。

6.1 为什么需要多进程：绕开 GIL

第 5 章的结论：CPU 密集任务多线程无效。多进程的思路釜底抽薪——每个进程拥有独立的解释器、独立的内存、独立的 GIL，各进程在多核上真正并行：

多线程：  [GIL]───线程1/线程2/线程3 轮流执行字节码        （并发不并行）
多进程：  进程1[GIL] 进程2[GIL] 进程3[GIL] 各自独立执行    （真并行，多核满载）

代价：进程创建更重（fork/spawn 需复制解释器）、进程间内存隔离——不能直接共享变量，通信必须序列化（pickle）跨进程传输，这部分开销是设计时的主要权衡点。

6.2 快速验证：CPU 密集任务的三种跑法

import time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def cpu_task(n: int) -> int:
    """纯计算：无 IO"""
    return sum(i * i for i in range(n))

N = 10_000_000

# 串行
start = time.perf_counter()
results = [cpu_task(N) for _ in range(4)]
print(f"串行:      {time.perf_counter() - start:.2f}s")

# 多线程（对照：应当几乎无加速）
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(cpu_task, [N] * 4))
print(f"多线程:    {time.perf_counter() - start:.2f}s")

# 多进程（应当接近 4 倍加速）
if __name__ == "__main__":
    start = time.perf_counter()
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(cpu_task, [N] * 4))
    print(f"多进程:    {time.perf_counter() - start:.2f}s")

# 典型输出（4 核机器）：
# 串行:   3.2s
# 多线程: 3.4s     ← GIL
# 多进程: 1.1s     ← 真·并行

注意多进程部分必须放在 if __name__ == "__main__": 里——原因见 6.3.2。

6.3 multiprocessing 核心

6.3.1 Process：最底层的进程对象

from multiprocessing import Process, current_process

def work(task_id: int):
    print(f"进程 {current_process().name} 处理任务 {task_id}")

if __name__ == "__main__":
    procs = [Process(target=work, args=(i,), name=f"worker-{i}") for i in range(3)]
    for p in procs:
        p.start()                    # 启动子进程
    for p in procs:
        p.join()                     # 等待结束；p.terminate() 可强制杀死
    print("全部子进程退出，退出码:", [p.exitcode for p in procs])

与 Thread 的 API 几乎一致（start/join/daemon/name），心智模型可以平移。

6.3.2 启动方式与 __main__ 保护（高频面试题）

子进程的创建方式由启动方法决定：

方法 机制 默认平台 对代码的要求
fork 复制父进程（写时复制），速度快 Linux/macOS 传统默认（Python 3.14 起 Unix 默认改为 forkserver） 无特殊要求
spawn 全新启动一个干净的解释器，重新 import 主模块 Windows、macOS 默认 目标函数/参数可 pickle；必须 __main__ 保护
forkserver 由一个干净的模板进程 fork 3.14 起 Unix 默认 目标函数/参数可 pickle

spawn 重新 import 主模块：若模块顶层就有 Process(...)、Pool(...)，import 时又去创建子进程，子进程再 import 再创建……无限增殖。if __name__ == "__main__": 就是判断"我是主模块直接运行，而不是被子进程 import"的开关——Windows 上不写必炸，跨平台代码一律写。

6.3.3 Pool 与 imap：批量并行

from multiprocessing import Pool

def scrape(url: str) -> dict:
    """模拟抓取并解析一个页面"""
    import time, random
    time.sleep(random.uniform(0.1, 0.5))     # 模拟耗时
    return {"url": url, "len": len(url) * 137}

if __name__ == "__main__":
    urls = [f"https://example.com/{i}" for i in range(20)]

    with Pool(processes=4) as pool:
        # map：结果有序、一次性全部返回
        results = pool.map(scrape, urls)

        # imap_unordered：惰性产出、先完成先返回 —— 适合边跑边处理
        for item in pool.imap_unordered(scrape, urls, chunksize=2):
            print("先到先得:", item["url"])

        # starmap：函数接受多个参数时解包调用
        pool.starmap(print, [("%s=%s",), ("a", 1)])   # 演示用
  • chunksize：任务分配粒度。任务数多且单个任务轻时，调大 chunksize 减少 IPC 次数；任务重时保持 1 即可。
  • imap（有序惰性）与 imap_unordered（无序惰性）的取舍见名知义。
  • 更推荐 concurrent.futures.ProcessPoolExecutor：与 ThreadPoolExecutor 同一套 API（submit/map/as_completed），线程/进程可无成本互换，异常处理也统一。

6.4 进程间通信（IPC）

进程内存隔离，共享数据必须显式通信。四种手段，按推荐度排序：

6.4.1 Queue：多进程消息传递（首选）

from multiprocessing import Process, Queue

def producer(q: Queue):
    for i in range(5):
        q.put(f"数据-{i}")
    q.put(None)                      # 结束信号

def consumer(q: Queue):
    while True:
        item = q.get()
        if item is None:
            break
        print(f"消费: {item}")

if __name__ == "__main__":
    q = Queue()
    p1 = Process(target=producer, args=(q,))
    p2 = Process(target=consumer, args=(q,))
    p1.start(); p2.start()
    p1.join()
    p2.join()

Queue 的经典死锁（官方文档特别警告）：子进程往队列 put 了大量数据但父进程还没取，此时父进程先 join() 等子进程——子进程的缓冲数据没被取走无法退出，父进程又在等子进程 → 互等死锁。正确顺序：先排空队列，再 join。

# 错误顺序：
p1.start()
p1.join()          # 子进程可能因队列缓冲未清而无法退出
print(q.get())     # 永远到不了这里

# 正确顺序：
p1.start()
while True:
    item = q.get()
    if item is None:
        break        # 先取完全部数据
    ...
p1.join()            # 此时子进程才能干净退出

6.4.2 Pipe：两个进程间的双向管道

from multiprocessing import Process, Pipe

def child(conn):
    conn.send({"status": "ok"})
    reply = conn.recv()                  # 双向：也能收
    print("子进程收到:", reply)
    conn.close()

if __name__ == "__main__":
    parent_conn, child_conn = Pipe()     # 默认双工
    p = Process(target=child, args=(child_conn,))
    p.start()
    print("主进程收到:", parent_conn.recv())
    parent_conn.send("收到，回执")
    p.join()

Queue（多对多、安全）vs Pipe（一对一、更快）：双方各有两个以上进程读写 Pipe 时会数据竞争，多进程场景一般选 Queue。

6.4.3 共享内存 Value / Array：少量数据的零拷贝共享

from multiprocessing import Process, Value, Array, Lock

def accumulate(counter, lock, arr):
    for _ in range(100_000):
        with lock:                       # 共享内存也要防竞态！
            counter.value += 1
    for i in range(len(arr)):
        arr[i] = arr[i] * 2

if __name__ == "__main__":
    counter = Value("i", 0)              # 'i' = C int
    arr = Array("d", [1.0, 2.0, 3.0])    # 'd' = double
    lock = Lock()

    procs = [Process(target=accumulate, args=(counter, lock, arr)) for _ in range(4)]
    for p in procs: p.start()
    for p in procs: p.join()

    print(counter.value)     # 400000
    print(arr[:])            # [2.0, 4.0, 6.0]

Value/Array 默认自带锁（lock=True），但复合操作（counter.value += 1）仍需显式 with lock。Python 3.8+ 还有更现代的 multiprocessing.shared_memory.SharedMemory（numpy 大数组跨进程零拷贝共享的正解）。

6.4.4 Manager：共享任意 Python 对象（灵活但慢）

from multiprocessing import Process, Manager

def update(shared: dict, worker_id: int):
    shared[f"worker-{worker_id}"] = worker_id * 10
    shared["counter"] += 1               # Manager 的 dict/list 自带代理锁

if __name__ == "__main__":
    with Manager() as mgr:
        shared = mgr.dict()
        shared["counter"] = 0
        procs = [Process(target=update, args=(shared, i)) for i in range(4)]
        for p in procs: p.start()
        for p in procs: p.join()
        print(dict(shared))   # {'worker-0': 0, ..., 'counter': 4}

Manager 启动一个服务进程，所有读写都是跨进程 RPC——用起来像普通 dict/list（还支持 Namespace、Lock），但每次操作都是序列化往返，性能差一个数量级，只适合低频配置类共享。

6.5 实战：并行图片处理骨架（ProcessPoolExecutor）

CPU 密集场景的通用模板：任务函数 + 进程池 + as_completed 汇报进度。

import time
from concurrent.futures import ProcessPoolExecutor, as_completed
from pathlib import Path

def process_image(path: Path) -> tuple[str, float]:
    """模拟重计算（灰度化/压缩等），替换为真实算法即可"""
    size_mb = path.stat().st_size / 1e6
    time.sleep(0.2 * max(size_mb, 0.1))       # 模拟耗时与文件大小相关
    return path.name, time.perf_counter() % 100

def batch_process(folder: Path, workers: int | None = None):
    files = list(folder.glob("*.png"))
    total = len(files)
    if total == 0:
        return
    with ProcessPoolExecutor(max_workers=workers) as pool:
        futures = {pool.submit(process_image, f): f for f in files}
        for done, fut in enumerate(as_completed(futures), 1):
            name, _ = fut.result()
            print(f"[{done}/{total}] 完成 {name}")

if __name__ == "__main__":                     # Windows/spawn 必需
    batch_process(Path("images"))

6.6 常见陷阱清单

  1. Windows/spawn 下没有 if __name__ == "__main__": → 子进程无限增殖（RuntimeError 或卡死）。跨平台代码 100% 要写。
  2. 闭包/lambda/嵌套函数传给进程池 → PicklingError。进程池的任务函数必须是模块顶层定义的（spawn 按名字导入），lambda 与内部函数无法 pickle。
  3. 任务参数或返回值太大：每次提交/返回都要 pickle 序列化，传 500MB 数组比计算本身还慢。大数据用 SharedMemory/numpy 共享或落文件传路径。
  4. Queue：先 join 后取数据 → 死锁（6.4.1）。
  5. 在子进程里访问父进程的全局对象：spawn 模式下子进程是全新的解释器，全局变量是重新初始化的副本，改动不会传回。
  6. 递归函数、打开的文件句柄/锁作为参数传递：不可 pickle。
  7. 每个任务都新建 Process：进程创建成本高（Windows 下数百毫秒），批量任务一律用池。
  8. daemon 进程自动被杀：与线程同理，不要让 daemon 子进程负责写关键数据。

6.7 本章小结

  • 多进程用"独立解释器 + 独立 GIL"实现真并行，是 CPU 密集任务的标准解法；代价是进程创建与 pickle 通信开销。
  • spawn（Windows/macOS 默认）重新 import 主模块 → 必须 __main__ 保护；任务函数必须模块顶层可 pickle。
  • IPC 优先级：Queue（消息传递首选）> Pool/Executor 返回值 > 共享内存 Value/Array/SharedMemory（大数据零拷贝）> Manager（灵活但慢）。
  • 与第 5 章共用 concurrent.futures 编程模型，线程/进程池可互换。

第 7 章 异步编程 asyncio

本章目标：建立"单线程事件循环"的心智模型；掌握 async/await、Task、gather/TaskGroup 的并发组织方式；学会异步超时与并发数控制；理解"协程里绝不能阻塞"的深层原因，并能规避常见错误。

前置：第 2 章生成器（协程的前身）、第 5 章 GIL（为什么 asyncio 不加速 CPU）。

7.1 心智模型：一个勤快的服务员

同步模型像一个服务员盯一桌客人从点菜到结账，期间干不了别的；多线程像雇很多服务员，人多了有管理成本；asyncio 则是一个服务员同时招呼几十桌——谁在等菜（IO），就先去照顾别人，菜好了（事件就绪）再回来上菜：

同步:    任务A [请求1][等待.........][响应1][请求2][等待.........][响应2]   总时长 = 累加
asyncio: 任务A [请求1]      [响应1]
         任务B   [请求2]      [响应2]                                        总时长 ≈ 最慢的那个
          ↑ 等待期间事件循环切换去执行其他任务

三个关键词：

  1. 单线程：整个程序只有一个线程（协程之间是"协作式"让出，不存在第 5 章的竞态条件）；
  2. 事件循环：一个 while 循环，不断问"哪个 socket 有数据了？哪个定时器到点了？"然后把 CPU 分给对应协程；
  3. await = 让出控制权：await 的地方是协程唯一可能被切换的点——这也是 asyncio 代码"线程安全"的原因：没有 await 的代码段是原子的。

适用判断：等待多、每次等待期间没多少计算 → asyncio 封神（千级并发连接）；CPU 计算 → 该用多进程（第 6 章）。

7.2 基础语法

7.2.1 协程函数与 await

import asyncio

async def fetch_data(delay: float) -> str:
    """async def 定义协程函数；调用它返回协程对象，并不执行！"""
    print(f"开始请求（等待 {delay}s）")
    await asyncio.sleep(delay)       # await：让出控制权给事件循环
    print("数据到达")
    return "数据"

async def main():
    result = await fetch_data(1.0)   # await 才真正执行协程，拿到返回值
    print("得到:", result)

asyncio.run(main())                  # 事件循环的启动入口（程序里只调用一次）
# 开始请求（等待 1.0s）
# 数据到达
# 得到: 数据

三条铁规则：

  1. async def 函数必须被 await（或包装成 Task）才会执行，直接调用只创建协程对象（忘 await 会得到 RuntimeWarning: coroutine ... was never awaited）。
  2. await 只能出现在 async def 内部。
  3. await 后面必须是 awaitable：协程、Task、Future，或支持 __await__ 的对象。

7.2.2 并发执行：顺序 await ≠ 并发

初学者最大误区：连续 await 是串行的：

async def main_bad():
    await fetch_data(1)      # 先等 1s
    await fetch_data(2)      # 再等 2s     总计 3s —— 并没有并发！

async def main_good():
    # 方式一：gather —— 最常用
    results = await asyncio.gather(
        fetch_data(1),
        fetch_data(2),
        fetch_data(3),
    )
    print(results)           # ['数据', '数据', '数据']，总耗时 ≈ 2s（最慢者）

    # 方式二：create_task —— 立刻"点火"让协程跑起来，之后随时 await
    task = asyncio.create_task(fetch_data(5))    # 已在后台运行
    await asyncio.sleep(1)                        # 此期间 fetch_data(5) 也在推进
    print("先干点别的...")
    print(await task)                             # 等 task 完成

gather(return_exceptions=True) 会把异常作为结果收集而不是中断整批；默认（False）则一个失败立即抛出（其余任务并不会被取消——这是 gather 的著名陷阱）。

7.2.3 TaskGroup：结构化并发（Python 3.11+，推荐）

async def main():
    async with asyncio.TaskGroup() as tg:            # 3.11+
        t1 = tg.create_task(fetch_data(1))
        t2 = tg.create_task(fetch_data(2))
    # 离开 async with 时：要么全部成功，要么全部取消——不可能漏网
    print(t1.result(), t2.result())

    # 任一任务抛异常 → 退出块时抛 ExceptionGroup，且其他任务已被自动取消

对比 gather，TaskGroup 的"块内任务全生命周期受管"正是结构化并发思想：没有孤儿任务、没有泄漏的后台协程。3.11+ 的新项目优先用它。

7.2.4 超时控制

# 方式一：wait_for（经典）
try:
    result = await asyncio.wait_for(fetch_data(10), timeout=2.0)
except TimeoutError:                       # 3.11+ 原生 TimeoutError
    print("超时，任务已被取消")

# 方式二：asyncio.timeout 上下文管理器（3.11+，可包住多个 await）
async with asyncio.timeout(2.0):
    r1 = await fetch_data(1)
    r2 = await fetch_data(5)               # r1 耗掉 1s 预算，r2 将超时

7.3 异步生态：与阻塞势不两立

7.3.1 大敌当前：协程里的阻塞调用

事件循环是单线程的——任何协程阻塞超过几毫秒，所有任务全部停摆：

async def bad():
    time.sleep(2)                # 灾难！同步 sleep 阻塞整个循环，其他任务全卡
    requests.get(url)            # 同样灾难：同步 HTTP 库
    with open("big.bin", "rb") as f:  # 小文件尚可，大文件 IO 同样阻塞
        f.read()

async def good():
    await asyncio.sleep(2)               # 异步 sleep：让出控制权
    await asyncio.to_thread(requests.get, url)   # 3.9+：把阻塞调用丢进线程池
    result = await loop.run_in_executor(None, cpu_func)  # CPU 任务丢进程池更佳

异步生态的正确姿势：HTTP 用 httpx（async 模式）或 aiohttp、数据库用 asyncpg/aiomysql/异步 ORM（SQLAlchemy 2.0 async）、文件用 aiofiles。混用同步库是 asyncio 第一大坑——排查方法：程序"卡死但 CPU 空闲"，八成是某处同步阻塞。

7.3.2 异步 HTTP 并发下载（需 pip install httpx）

import asyncio
import httpx

async def fetch(client: httpx.AsyncClient, url: str) -> tuple[str, int]:
    resp = await client.get(url)
    return url, resp.status_code

async def main():
    urls = [f"https://httpbin.org/delay/1" for _ in range(10)]
    async with httpx.AsyncClient(timeout=10) as client:   # 复用连接池
        results = await asyncio.gather(
            *(fetch(client, u) for u in urls), return_exceptions=True
        )
    for r in results:
        print(r if not isinstance(r, Exception) else f"失败: {r}")

asyncio.run(main())
# 10 个"各等 1 秒"的请求，总耗时约 1~2 秒（而非 10 秒+）

7.4 异步迭代器与异步上下文管理器

async 版协议与第 2/3 章的同步协议一一对应：

import asyncio

class AsyncTicker:
    """异步迭代器：每秒产出一个计数（async for 消费）"""
    def __init__(self, stop):
        self.stop, self.i = stop, 0

    def __aiter__(self):
        return self

    async def __anext__(self):
        if self.i >= self.stop:
            raise StopAsyncIteration
        await asyncio.sleep(0.5)
        self.i += 1
        return self.i

async def main():
    async for tick in AsyncTicker(3):
        print("tick", tick)

    # 异步上下文管理器：__aenter__ / __aexit__
    # async with httpx.AsyncClient() as client: ...   ← 前面已经在用

asyncio.run(main())

异步生成器（async def + yield）可以直接写 async for 的数据源；注意它需要 contextlib.aclosing() 或显式 aclose() 做清理。

7.5 实战：带限流、超时、重试的并发抓取器

import asyncio
import random
from dataclasses import dataclass

@dataclass
class Result:
    url: str
    ok: bool
    detail: str

async def fetch_once(url: str, sem: asyncio.Semaphore) -> str:
    async with sem:
        # 用纯标准库模拟一次"网络请求"（真实场景替换为 httpx）
        await asyncio.sleep(random.uniform(0.1, 0.8))
        if random.random() < 0.3:
            raise ConnectionError("模拟网络抖动")
        return f"{url} 的内容({len(url) * 100} bytes)"

async def fetch_with_retry(url: str, sem: asyncio.Semaphore,
                           retries: int = 3) -> Result:
    last_err: Exception | None = None
    for attempt in range(1, retries + 1):
        try:
            async with asyncio.timeout(1.0):          # 单次尝试 1s 超时
                body = await fetch_once(url, sem)
            return Result(url, True, body)
        except (TimeoutError, ConnectionError) as e:
            last_err = e
            await asyncio.sleep(0.2 * attempt)        # 指数退避的简化版
    return Result(url, False, f"重试 {retries} 次仍失败: {last_err}")

async def main():
    urls = [f"https://api.example.com/item/{i}" for i in range(15)]
    sem = asyncio.Semaphore(5)                        # 全局并发上限 5
    results = await asyncio.gather(
        *(fetch_with_retry(u, sem) for u in urls)
    )
    ok = [r for r in results if r.ok]
    print(f"成功 {len(ok)}/{len(results)}")
    for r in results:
        if not r.ok:
            print("失败:", r.url, r.detail)

if __name__ == "__main__":
    asyncio.run(main())

这个"Semaphore 限流 + timeout 超时 + 重试退避 + gather 汇总"的四件套，就是生产级异步 IO 任务的骨架。

7.6 常见陷阱清单

  1. 忘记 await：fetch_data(1) 直接调用什么都不会发生，只有 RuntimeWarning 提示。
  2. 协程中调用阻塞函数（time.sleep、requests、重 CPU 计算）：整个循环卡死。阻塞任务丢 asyncio.to_thread，CPU 任务丢进程池。
  3. 顺序 await 误当并发：await a(); await b() 是串行；并发用 gather/TaskGroup/create_task。
  4. gather 一个失败、其余任务成为孤儿：需要"全有或全无"时用 TaskGroup 或 return_exceptions=True 后统一处理。
  5. 一程序多次 asyncio.run() / 在已有循环里再 run：asyncio.run 每次新建事件循环，一个程序通常只在入口调一次；库代码不要自己 run。
  6. 无限 gather：一万并发打爆自己与对方，务必 Semaphore 限流。
  7. 在任务里引用了即将销毁的对象/忘记持引用：create_task 返回的 Task 若不保存引用，可能被垃圾回收导致任务神秘消失——保存到集合或变量里。
  8. 混用同步与异步世界：同步框架（Flask）里调 async 函数、异步框架里调同步重库，都是事故源。

7.7 本章小结

  • asyncio = 单线程 + 事件循环 + await 让出；await 点是唯一的切换点，没有 await 的代码段天然原子。
  • 并发组织：gather（简单批量）、TaskGroup（3.11+ 结构化并发，推荐）、create_task（后台点火）；超时用 wait_for/asyncio.timeout；限流用 Semaphore。
  • 协程里绝不阻塞：同步库换异步库，或 to_thread/run_in_executor 委托；"CPU 密集 → 进程池"的边界永不改变。
  • 四件套骨架（限流 + 超时 + 重试 + gather）覆盖绝大多数异步 IO 场景。

8.1 属性访问的两层协议

8.1.1 __getattr__：兜底回调

class LazyRecord:
    """只有访问"不存在"的属性时才会被调用"""
    def __init__(self):
        self.known = 42

    def __getattr__(self, name):
        print(f"常规查找失败，兜底生成 {name}")
        value = f"<{name} 的懒加载值>"
        setattr(self, name, value)     # 缓存起来，下次不再进 __getattr__
        return value

r = LazyRecord()
print(r.known)      # 42          —— 正常找到，不触发 __getattr__
print(r.anything)   # 兜底生成 anything → <anything 的懒加载值>
print(r.anything)   # <anything 的懒加载值>  —— 已缓存进实例，第二次不再触发

注意与 __getattribute__ 的区别：

  • __getattr__：仅当常规查找全部失败时调用——安全的"兜底"钩子；
  • __getattribute__：所有属性访问都会经过它——全权拦截，但极易写出无限递归（内部再访问属性又触发自己），必须显式走 super().__getattribute__(name)。

__getattr__ 的典型应用：代理对象、REST 客户端的链式资源访问、兼容旧接口的适配层：

class APIProxy:
    """api.users.posts.list() 自动转成 GET /users/posts/list"""
    def __init__(self, segments=()):
        self._segments = segments

    def __getattr__(self, name):
        return APIProxy(self._segments + (name,))

    def __call__(self, **params):
        path = "/" + "/".join(self._segments)
        return f"GET {path} params={params}"

print(APIProxy().users.posts.list(limit=10))
# GET /users/posts/list params={'limit': 10}

8.1.2 属性查找的完整顺序（一图流）

obj.attr 的查找顺序：
1. 数据描述符（同时定义 __get__ 和 __set__）：type(obj).__mro__ 上找到即优先  ← property 在这里
2. 实例的 __dict__
3. 非数据描述符（只有 __get__）：类及父类上                      ← 函数/staticmethod/classmethod 在这里
4. __getattr__ 兜底

这条链解释了大量"为什么"：为什么方法不会覆盖 property、为什么类属性能当默认值、为什么实例遮不住类上的 property。

8.2 描述符：property 的本质

8.2.1 协议与最小示例

描述符是"定义了 __get__/__set__/__delete__ 之一的类"，它让属性访问可以被劫持并代理：

class Positive:
    """数据描述符：强制属性为正数"""
    def __set_name__(self, owner, name):        # 3.6+：类创建时自动获知自己叫什么
        self.private_name = "_" + name          # 如 price → _price

    def __get__(self, obj, objtype=None):
        return getattr(obj, self.private_name)

    def __set__(self, obj, value):
        if not isinstance(value, (int, float)) or value <= 0:
            raise ValueError(f"{self.private_name[1:]} 必须是正数，收到 {value!r}")
        setattr(obj, self.private_name, value)

class Order:
    price = Positive()          # 描述符实例作为类属性
    quantity = Positive()       # 同一个类可复用

    def total(self):
        return self.price * self.quantity

o = Order()
o.price = 9.9        # 触发 Positive.__set__ → 校验
o.quantity = 3
print(o.total())     # 29.7 —— o.price 触发 Positive.__get__
o.price = -1         # ValueError: price 必须是正数，收到 -1

8.2.2 揭秘：property 就是一个描述符

class Temperature:
    @property
    def celsius(self): ...

# 等价于（简化）：
celsius = property(lambda self: self._celsius, set_celsius)
print(type(Temperature.__dict__["celsius"]))   # <class 'property'>
print(hasattr(property, "__get__"), hasattr(property, "__set__"))   # True True

第 1 章 1.5.1 用过的 @property，底层就是"数据描述符 + 装饰器"的语法糖。标准库中 classmethod、staticmethod、函数本身（非数据描述符，所以 obj.method 每次产出绑定的方法对象）全是描述符——理解描述符 = 理解 Python 属性系统的底层。

8.2.3 描述符 vs property 怎么选

  • 一两个属性的简单校验 → @property 直观；
  • 同一套校验逻辑要复用到多个/多个类的多个属性 → 描述符（如上面的 Positive，ORM 字段系统的原理）。

8.3 __new__、单例与 MRO

8.3.1 __new__ 与 __init__ 的分工

  • __new__(cls, ...)：静态创建实例（先调用），负责"造出对象"，返回实例；
  • __init__(self, ...)：初始化刚造好的实例（后调用），只负责"配置对象"，返回 None。

__new__ 常用于单例与不可变类型：

class Singleton:
    _instance = None
    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

a, b = Singleton(), Singleton()
print(a is b)     # True

单例在 Python 中更地道的三种替代：① 直接用模块级实例（模块天然单次导入）；② functools.lru_cache 缓存工厂函数；③ 依赖注入容器。__new__ 单例注意子类化会共享实例的坑。

8.3.2 MRO 与 super() 的真相

多继承的方法查找顺序由 C3 线性化算法决定，可查看 cls.__mro__：

class Base:
    def ping(self): print("Base.ping")

class A(Base):
    def ping(self):
        print("A.ping 前")
        super().ping()          # ← 不是"父类"，而是 MRO 中的下一个类！

class B(Base):
    def ping(self):
        print("B.ping 前")
        super().ping()

class C(A, B):                  # C 的 MRO: C → A → B → Base → object
    def ping(self):
        print("C.ping 前")
        super().ping()

C().ping()
# C.ping 前
# A.ping 前
# B.ping 前
# Base.ping
print([c.__name__ for c in C.__mro__])   # ['C', 'A', 'B', 'Base', 'object']

super() 的正确定义：沿 MRO 找下一个类，而非"我的父类"。这使得多继承下每个类在整条 MRO 链上只被调用一次（协作式多继承），是 Mixin 模式的安全基础。设计多继承时遵循两个纪律：① Mixin 只做一件小事且尽量自带默认实现；② 所有跨 Mixin 调用的方法签名保持一致。

8.4 元类与 __init_subclass__

8.4.1 类也是对象：type 的三参形式

类本身是 type 的实例——"类的类"就是元类：

Dog = type("Dog", (object,), {"sound": "汪", "bark": lambda self: self.sound * 2})
print(Dog().bark())        # 汪汪

# class 语句的底层就是这个调用
class Cat: pass
print(type(Cat))           # <class 'type'>
print(isinstance(Dog, type))   # True

自定义元类可以拦截"类的创建过程"（注意：不是实例的创建）：

class AutoRegister(type):
    """任何使用本元类的子类，创建时自动注册"""
    registry: dict[str, type] = {}

    def __new__(mcls, name, bases, namespace, **kwargs):
        cls = super().__new__(mcls, name, bases, namespace)
        if bases:                          # 跳过基类自身
            mcls.registry[name] = cls
        return cls

class Exporter(metaclass=AutoRegister): pass

class CsvExporter(Exporter): pass
class JsonExporter(Exporter): pass

print(AutoRegister.registry)   # {'CsvExporter': <class ...>, 'JsonExporter': <class ...>}

8.4.2 现代替代品：__init_subclass__（优先使用）

元类"杀鸡用牛刀"且多继承元类会冲突。绝大多数"拦截子类定义"的需求，3.6+ 用钩子方法就够：

class Plugin:
    registry: dict[str, type] = {}

    def __init_subclass__(cls, *, name: str | None = None, **kwargs):
        super().__init_subclass__(**kwargs)       # 必须先交还链路
        Plugin.registry[name or cls.__name__] = cls

class CSVPlugin(Plugin, name="csv"): pass
class XMLPlugin(Plugin, name="xml"): pass

print(list(Plugin.registry))       # ['csv', 'xml']

选型口径：能 __init_subclass__ 就不写元类。需要全项目级"类的行为改写"（如 Django Model、SQLAlchemy Declarative 那种把类属性翻译成表结构的深度魔法）才是元类的正当舞台。ORM 模型类的原理：元类扫描 CharField() 这类描述符属性并登记成表字段——描述符（8.2）+ 元类（本节）的组合。

8.5 现代工具箱

8.5.1 dataclass：声明式数据类

from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)          # 不可变 + 无 __dict__（3.10+ 组合）
class Money:
    amount: int
    currency: str = "CNY"
    tags: list[str] = field(default_factory=list)   # 可变默认值必须 factory

m = Money(100)
print(m)                  # Money(amount=100, currency='CNY', tags=[])
m2 = Money(100)
print(m == m2)            # True（值相等；frozen 还带来可哈希，能进 set/dict 键）
# m.amount = 200          # FrozenInstanceError

常用参数：order=True 自动生成比较方法（可排序）、kw_only=True（3.10+）强制关键字传参、__post_init__ 做派生字段初始化。与 typing.NamedTuple 的区别：NamedTuple 是元组（支持解包/不可变），dataclass 是普通类（灵活可变）。

8.5.2 Enum：类型安全的常量

from enum import Enum, auto

class OrderStatus(Enum):
    PENDING = auto()
    PAID = auto()
    SHIPPED = auto()
    CANCELED = auto()

print(OrderStatus.PAID.name, OrderStatus.PAID.value)   # PAID 2
print(OrderStatus("PAID") if False else OrderStatus["PAID"])   # OrderStatus.PAID（按名取）
# 用裸字符串/整数表示状态时，非法值只能在运行深处爆雷；Enum 让非法值在赋值处就报错

3.11+ 有 StrEnum（枚举值即字符串，序列化方便）；IntEnum 可与整数比较。

8.5.3 ABC：抽象基类强制契约

from abc import ABC, abstractmethod

class Storage(ABC):
    @abstractmethod
    def save(self, key: str, data: bytes) -> None: ...

    @abstractmethod
    def load(self, key: str) -> bytes: ...

    def save_json(self, key: str, obj) -> None:    # 模板方法：公共逻辑写基类
        import json
        self.save(key, json.dumps(obj).encode())

class MemoryStorage(Storage):
    def __init__(self):
        self._data: dict[str, bytes] = {}
    def save(self, key, data): self._data[key] = data
    def load(self, key): return self._data[key]

# Storage()          # TypeError: 抽象类不能实例化 —— 漏实现 save/load 的子类同样报错
print(MemoryStorage().save_json("k", {"a": 1}) or "ok")

8.5.4 Protocol：静态鸭子类型（更 Pythonic 的契约）

ABC 要求"显式继承"才承认子类型；Protocol（PEP 544，3.8+）只看方法签名是否匹配——像鸭子类型一样宽松，又能被 mypy 静态检查：

from typing import Protocol, runtime_checkable

@runtime_checkable
class Closer(Protocol):
    def close(self) -> None: ...

def cleanup(resource: Closer):        # 任何"有 close() 的对象"都满足，无需继承
    resource.close()

cleanup(open("f.txt"))                # 文件对象 ✔
cleanup(MemoryStorage())              # 报错？不——MemoryStorage 没有 close 才会
                                      # 这里仅为演示：有 close() 的第三方类无需任何改造即可传入

选型：库作者想定义"接口"给用户实现 → ABC；想标注"我接受任何能做 X 的对象" → Protocol。后者与鸭子类型精神一致，是现代 Python 的推荐默认。

8.7 常见陷阱清单

  1. __getattribute__ 里直接 self.x → 无限递归；必须 super().__getattribute__(name)。
  2. __eq__ 定义了但 __hash__ 没配套：可变字段参与哈希会让对象在 dict/set 中"失踪"；默认 __hash__ 会被自定义 __eq__ 置为 None。
  3. 可变类属性当实例默认值：class A: items = [] 所有实例共享同一列表；应在 __init__ 里 self.items = []。
  4. 以为 super() 是父类：是 MRO 下一站；菱形继承里理解错误会导致方法漏调或重调。
  5. 滥用继承："has-a 用组合，is-a 才继承"；组合优先是工程默认。
  6. dataclass 可变默认值：field(default=[]) 直接报错是保护，正确写法 default_factory=list。
  7. 元类炫技：能 __init_subclass__/装饰器解决的别上元类，可读性是最大成本。

8.8 本章小结

  • 属性访问链：数据描述符 > 实例 __dict__ > 非数据描述符/类属性 > __getattr__；__getattr__ 是安全兜底，__getattribute__ 是高危全拦截。
  • 描述符协议是 property/方法绑定/ORM 字段的共同底层；同一校验逻辑复用多属性时用描述符。
  • __new__ 造对象、__init__ 配置对象；super() 是 MRO 下一站而非父类。
  • 元类拦截"类的创建"，__init_subclass__ 是它的轻量现代替代；深度框架才用元类。
  • 现代 OOP 三板斧：dataclass（数据）、Enum（状态）、Protocol/ABC（契约）——先 Protocol 后 ABC。

9.1.2 为什么用 src 布局而不是把包放在根目录

根目录放包（flat layout）有一个经典事故：本地 import myproject 永远命中源码目录而非已安装包——"本地好好的，装到别人机器就崩"或"测试测的是旧包"。src 布局强制"必须先安装（可编辑安装 pip install -e .）才能导入"，测试环境 = 部署环境，这类问题从根上消失。这也是 pytest、pip、requests 等主流项目的选择。

其他纪律：

  • tests/ 与源码镜像，看到测试路径就知道在测谁；
  • 业务核心（core）不 import 框架代码——换 Web 框架/换数据库不动核心逻辑；
  • 脚本、notebook、实验代码不进 src/。

# 比较：与 None/True/False 用 is；序列/字典判空用真值
if result is None: ...          # ✅  not `result == None`
if not items: ...               # ✅ 空列表/空串都为 False
if key in mapping: ...          # ✅ 而不是 `key in mapping.keys()`

# 字符串拼接一律 f-string（3.6+；3.8+ 支持自文档化）
print(f"{user.name=} {score:.2f}")     # user.name='张三' score=91.50

# 用 pathlib 而非 os.path 字符串手术；用 dataclass 而非传一堆散参数
# 每行 ≤ 88 字符（black 默认）；顶层函数/类定义间空 2 行，方法间空 1 行

还有一条"向语言要效率"的现代写法清单：字典合并 merged = {**a, **b} 或 a | b（3.9+）、海象运算符 while chunk := f.read(8192):（3.8+）、match/case 结构分支（3.10+，复杂分支比 if 链清晰）。

9.4 类型注解：现代 Python 的基础设施

9.4.1 为什么要注解

类型注解不改变运行时行为，但带来：IDE 精确补全与重构、mypy 提前抓 bug、代码即文档、接口契约显式化。当代 Python 项目（尤其多人协作）注解是标配。

9.4.2 语法速成（3.10+ 现代写法）

def process_orders(
    orders: list[dict[str, float]],     # 3.9+ 直接用内建容器，无需 typing.List
    threshold: float = 100.0,
    tag: str | None = None,             # 3.10+ 用 | 代替 Optional[str]
) -> tuple[int, float]:                 # 返回 (笔数, 总额)
    ...

# 常用类型工具
from collections.abc import Callable, Iterable, Iterator   # 3.9+ 用 abc 版
from typing import Final, Literal, TypeVar, TypedDict

MAX_USERS: Final = 1000                            # 常量（mypy 禁止重绑定）
Mode = Literal["read", "write"]                    # 字符串枚举约束

class UserDict(TypedDict):                         # 带类型的字典结构
    name: str
    age: int

T = TypeVar("T")
def first(items: list[T]) -> T | None:             # 泛型函数：输入 list[X] 返回 X
    return items[0] if items else None

class Repo(Generic[T]):                            # 泛型类（3.12+ 可写 class Repo[T]:）
    ...

9.4.3 渐进式落地

  1. 新代码全部注解；旧代码按"被改动到就顺手加"推进。
  2. 库/公共 API 100% 注解，并放 py.typed 标记文件。
  3. 配 mypy（或 pyright）进 CI，先宽松后收紧：
# pyproject.toml

python_version = "3.10"
warn_unused_ignores = true

# 起步阶段对历史代码豁免，新目录逐步纳入 strict
[[tool.mypy.overrides]]

边界情况用 typing.cast() 显式声明（比 # type: ignore 诚实）；第三方库无注解时 ignore_missing_imports 定向豁免。

9.5 异常处理规范

# 原则一：捕获具体异常，禁止裸 except
try:
    resp = httpx.get(url, timeout=10)
except httpx.TimeoutException:          # ✅ 精确
    ...
# except:                               # ❌ 连 KeyboardInterrupt/SystemExit 都吞

# 原则二：要么处理（降级/重试/转换），要么抛出——不要 log 完又 raise 的"既管又不管"
try:
    save_config(data)
except OSError:
    logger.exception("配置写入失败，继续用内存配置运行")   # 处理了：降级
    fallback_config = data

# 原则三：跨层传递时用异常链保留现场
try:
    parse(raw)
except json.JSONDecodeError as e:
    raise ValueError(f"第 {e.lineno} 行配置非法") from e
    # from e 保留原始异常为 __cause__，堆栈完整可追

# 原则四：定义异常层次，让调用方能按层捕获
class AppError(Exception): ...
class ConfigError(AppError): ...
class NetworkError(AppError):
    def __init__(self, url: str, cause: Exception):
        super().__init__(f"请求 {url} 失败")
        self.url = url

四条加分项：

  • EAFP 风格是 Python 惯例：直接 try/except 而不是先 if 检查（try: return d[k] except KeyError: 优于 if k in d:——无竞态且更快）；
  • 在边界统一兜底：main()/CLI 入口/框架中间件 catch 一次 AppError 转友好提示 + 非 0 退出码 + 日志，内部代码尽管放心抛；
  • 自定义异常只做"类层次 + 关键字段"，避免继承自 BaseException；
  • finally/else 子句语义要清楚：else = 无异常才执行，让 try 块尽量小。

9.6 日志规范

9.6.1 用 logging，不用 print

print 无法分级、无时间戳、不能关闭、无法接收集/报警系统。标准姿势：

import logging

logger = logging.getLogger(__name__)     # 每个模块一个以 __name__ 命名的 logger
                                         # 形成层级树 myproject.core.service
def transfer(from_acc: str, to_acc: str, amount: float) -> None:
    logger.info("转账开始 %s -> %s 金额=%.2f", from_acc, to_acc, amount)
    # 两个习惯：
    # ① 用 %s 延迟格式化（级别不够时省字符串拼接开销）
    # ② 别用 f-string 拼日志参数
    try:
        _do_transfer(from_acc, to_acc, amount)
    except InsufficientFunds as e:
        logger.exception("转账失败 %s -> %s", from_acc, to_acc)   # 自动附完整堆栈
        raise

9.6.2 应用入口统一配置（库不要配置！）

# logging_setup.py —— 只在应用入口调用一次
import logging
from logging.handlers import RotatingFileHandler

def setup_logging(level: str = "INFO", logfile: str = "app.log") -> None:
    fmt = "%(asctime)s %(levelname)-8s %(name)s:%(lineno)d %(message)s"
    handler = RotatingFileHandler(          # 按大小轮转，防止日志撑爆磁盘
        logfile, maxBytes=10 * 1024 * 1024, backupCount=5, encoding="utf-8"
    )
    handler.setFormatter(logging.Formatter(fmt))
    logging.basicConfig(level=level, handlers=[handler])

库的纪律：只 logger = logging.getLogger(__name__) 并发日志，绝不配置 handler/格式——配置权属于最终应用，否则库会污染宿主程序的日志体系。

级别使用口径：DEBUG（诊断细节，生产默认关）/ INFO（正常业务事件，如"订单创建"）/ WARNING（可自愈异常，如"重试第 2 次"）/ ERROR（本次操作失败）/ CRITICAL（进程级灾难）。

9.7 测试规范

9.7.1 pytest 基本姿势

测试文件 test_*.py、函数 test_*，断言直接用 assert（失败时 pytest 自动给出左右值对比）：

# src/myproject/core/discount.py
def discount(price: float, vip: bool) -> float:
    if price < 0:
        raise ValueError("价格不能为负")
    return price * 0.8 if vip else price

# tests/unit/test_discount.py
import pytest
from myproject.core.discount import discount

def test_vip_gets_20_percent_off():
    assert discount(100, vip=True) == 80          # Arrange-Act-Assert 三段式

def test_normal_price_unchanged():
    assert discount(100, vip=False) == 100

def test_negative_price_raises():                  # 异常断言
    with pytest.raises(ValueError, match="不能为负"):
        discount(-1, vip=False)

@pytest.mark.parametrize(                          # 参数化：一个测试跑多组数据
    ("price", "vip", "expected"),
    [(100, True, 80), (100, False, 100), (50, True, 40)],
)
def test_discount_table(price, vip, expected):
    assert discount(price, vip) == expected

9.7.2 fixture 与 monkeypatch

import pytest

@pytest.fixture
def temp_config(tmp_path):                 # 内置 tmp_path：每个测试独立的临时目录
    cfg = tmp_path / "app.json"
    cfg.write_text('{"theme": "dark"}', encoding="utf-8")
    return cfg                             # yield 前是准备，之后是清理（第 3 章）

def test_reads_config(temp_config):
    assert temp_config.exists()

def test_fetch_uses_env(monkeypatch):      # monkeypatch：替身环境变量/属性，测试后自动还原
    monkeypatch.setenv("API_KEY", "fake")
    assert get_api_key() == "fake"

9.7.3 测试纪律

  • 测试金字塔：大量单元测试（快、隔离）+ 适量集成测试（真实依赖）+ 少量端到端；
  • 测试之间零共享状态（不共享文件、数据库行、环境变量），顺序无关；
  • 覆盖率作为"发现漏测"的仪表（pytest --cov=myproject --cov-report=term-missing），不是 KPI——追求关键分支覆盖，不刷数字；
  • 给每个 bug 先写一个能复现它的失败测试，再修（回归测试护栏）。

9.10 配置与密钥管理

# config.py —— pydantic-settings：声明式 + 校验 + 类型安全（需 pydantic-settings）
from pydantic_settings import BaseSettings

class Settings(BaseSettings):

    debug: bool = False
    database_url: str                    # 必填：缺失时启动即报错，而不是运行中炸

    model_config = {"env_file": ".env", "env_file_encoding": "utf-8"}
